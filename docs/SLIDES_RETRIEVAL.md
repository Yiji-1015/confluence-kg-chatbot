# 슬라이드 1 · 임베딩 스키마

## 한 줄 메시지

> **무엇을 어떤 타입으로 저장할지가 검색으로 할 수 있는 일을 결정한다.**

## 실제로 색인된 문서 하나

Confluence 문서 한 건은 800자 단위로 쪼개져 이런 모양으로 저장된다.

```json
{
  "chunk_id":     "21102704_chunk_0",
  "doc_id":       "21102704",
  "title":        "주차 지원 기준",
  "text":         "우대빌딩 주차\n위치 : B1F~B3F\n비용 : 2,000원/30분 ...",
  "space_key":    "LLOYDK",
  "author":       "(작성자)",
  "url":          "https://.../wiki/spaces/...",
  "category":     "LLOYDK에 오신 걸 환영합니다!",
  "path":         "LLOYDK / LLOYDK에 오신 걸 환영합니다! / People / 주차 지원 기준",
  "updated_at":   "2026-09-02T02:16:51.205Z",
  "chunk_index":  0,
  "total_chunks": 2,
  "text_vector":  [0.0123, -0.0456, ... ]   // 1536개
}
```

문서 583건 → 청크 3,211개. (Confluence에서 640건을 가져왔고 57건은 본문이 비어 있었다.)

## 필드 13개, 목적은 다섯 가지

| 목적 | 필드 | 타입 | 이 타입인 이유 |
|---|---|---|---|
| **검색된다** | `title`, `text` | `text` + `nori_analyzer` | 형태소로 쪼개 색인해야 부분 일치 검색이 된다 |
| **의미 검색** | `text_vector` | `dense_vector` (1536, cosine) | 임베딩 벡터의 코사인 유사도 |
| **거르고 찾는다** | `doc_id`, `chunk_id`, `space_key`, `author`, `category`, `path`, `url` | `keyword` | 쪼개지 않아야 정확 일치와 집계가 된다 |
| **비교·정렬** | `updated_at` | `date` | 증분 색인 비교 + 최신 문서 가산점 |
| **순서 복원** | `chunk_index`, `total_chunks` | `integer` | 청크를 원문 순서대로 다시 이어붙일 때 |

## `text`와 `keyword`의 차이 — 이 매핑의 중심축

| | `text` | `keyword` |
|---|---|---|
| 저장 방식 | 형태소로 **쪼개서** | **통째로** |
| 답하는 질문 | "이 단어를 **포함**하는가" | "이 값과 **정확히 같은가**" |
| `"솔루션/개발"`을 넣으면 | `솔루션` `개발` 두 토큰 | `솔루션/개발` 한 덩어리 |

`category`를 `text`로 뒀다면 `"솔루션/개발"`이 쪼개져 **정확 필터와 집계가 깨진다.**
반대로 `text`를 `keyword`로 뒀다면 본문 전체가 한 덩어리라 **검색이 아예 불가능하다.**

## 한국어 분석기 — 필터 3종

```json

},
"filter": {

```

세 설정 모두 **빠뜨렸다가 실제로 검색이 틀려서 넣은 것**이다.

### ① `nori_part_of_speech` — 조사·어미를 뺀다

없을 때는 조사와 어미가 전부 검색어가 된다.

```
질문: "Jira 서버에서 Claude가 어떤 작업들을 할 수 있는지 알려줘"

필터 없음 (21개): jira 서버 에서 claude 가 어떤 작업 들 을 할 하 ᆯ 수 있 는지 알려 알리 어 줘 주 ㅓ
필터 있음 (12개): jira 서버 claude 작업 할 하 수 있 알려 알리 줘 주
```

**왜 문제인가:** 사내 문서는 대부분 격식체라 `줘` 같은 어미가 드물다.
드문 단어는 BM25가 "변별력이 높다"고 판단한다(`줘`의 IDF = 4.624).
그래서 **구어체로 쓰인 문서 하나가 아무 질문에나 1위로 올라왔다.**

실제로 위 질문의 BM25 1위 문서(39.59점)를 Elasticsearch `_explain`으로 분해한 결과:

| 토큰 | 점수 기여 | 정체 |
|---|---|---|
| `주 ㅓ` | **8.17** | "알려**줘**"의 어미 |
| `줘` | **6.77** | 〃 |
| `알려` | 4.43 | "**알려**줘" |
| `는지` | 3.89 | "할 수 있**는지**" |
| `어떤` | 2.82 | 의문 관형사 |
| **`jira`** `claude` `서버` | **0 / 0 / 0** | 그 문서에 아예 없음 |

정작 정답 문서에는 `jira` 17회, `claude` 21회, `서버` 19회가 있었는데 4위였다.

### ② `lowercase` — 영문 대소문자를 통일한다

```
없을 때: 'BlackBird' → ['BlackBird']     'blackbird' → ['blackbird']   서로 다른 토큰
있을 때: 둘 다 → ['blackbird']
```

| 질의 | 필터 없을 때 1위 | 필터 있을 때 1위 |
|---|---|---|
| `HashiCorp 자격증` | HashiCorp 자격증 취득현황 (41.86) | HashiCorp 자격증 취득현황 (55.05) |
| `hashicorp 자격증` | **MongoDB 자격증 관련 (25.46)** ❌ | HashiCorp 자격증 취득현황 (55.05) ✅ |

사내 문서에는 `lk-ocr-api`, `BlackBird`, `HashiCorp`, `MCP` 같은 영문 고유명사가 많고,
사용자가 소문자로 칠 가능성이 높다.

### ③ `decompound_mode: mixed` — 복합명사의 원형을 남긴다

| 단어 | `discard` (기본값) | `mixed` (적용) |
|---|---|---|
| 주차장 | `['주차', '장']` | `['주차장', '주차', '장']` |
| 출장비 | `['출장', '비']` | `['출장비', '출장', '비']` |
| 회의록 | `['회의', '록']` | `['회의록', '회의', '록']` |
| 전산실 | `['전산', '실']` | `['전산실', '전산', '실']` |

`주차장`이라는 통짜 토큰은 희소해 점수가 크고, `주차`·`장`은 흔해 기여가 작다.
`discard`에서는 "주차장"으로 물어도 흔한 조각으로만 매칭돼 변별이 되지 않았다.

## 설계 판단 3가지

| 판단 | 이유 |
|---|---|
| `chunk_id`를 Elasticsearch `_id`로 사용 | 같은 청크를 다시 색인하면 중복 저장이 아니라 **자동 덮어쓰기(upsert)** |
| 실제 인덱스 위에 **별칭**을 붙임 | 별칭 이름으로 인덱스를 만들면 갈아끼울 이름표가 사라져 무중단 재색인 경로가 막힌다 |
| `number_of_shards`는 코드에, `number_of_replicas`는 코드 밖에 | shard 수는 **인덱스 생성 시에만** 정할 수 있어 코드에 둔다. replica 수는 런타임에 바꿀 수 있고 노드 수에 따라 달라지는 **배포 환경의 값**이라 코드가 정하지 않는다 |

# 슬라이드 2 · 검색 알고리즘 + 평가

## 한 줄 메시지

> **두 검색을 합치는 이유는 평균을 올리려는 게 아니라 바닥을 받치려는 것이다.**

## 전체 흐름 6단계

```
질문
 │
 ├─① BM25 키워드 검색  → 후보 청크 50개 ┐
 └─② kNN  의미 검색    → 후보 청크 50개 ┘
                             │
                    ③ 각 리스트의 순위로 1/(60+순위)를 구해 합산 (RRF)
                             │
                    ④ 최신 문서 가산점 (최대 결합 점수의 4%)
                             │
                    ⑤ 점수순 정렬 후 "서로 다른 문서" 5건 선별
                             │
                    ⑥ 그 5개 문서의 전체 청크를 이어붙여 LLM에 전달
```

주요 설정값 — 모두 `.env`로 빠져 있어 재색인 없이 재시작만으로 바뀐다.

| 설정 | 값 | 뜻 |
|---|---|---|
| `RETRIEVAL_CANDIDATE_SIZE` | `50` | 각 검색이 가져올 후보 **청크** 수 |
| `RETRIEVAL_TOP_K` | `5` | 최종 컨텍스트에 넣을 **서로 다른 문서** 수 |
| `RRF_K` | `60` | 순위 결합 상수. `1/(RRF_K + 순위)`를 각 리스트에서 구해 더한다 |
| `RECENCY_BOOST_MAX` | `0.04` | 최신 문서 가산점. 이론상 최대 결합 점수의 **4%** |
| `DOC_CONTEXT_MAX_CHARS` | `3000` | 문서 하나에서 이어붙일 최대 글자 수 |

|---|---|

직원은 "일한", "쉴"이라고 묻고 문서는 "근속", "휴가"라고 쓴다.

## ① BM25 — 키워드가 몇 번, 얼마나 드물게 나오는가

$$\text{BM25}(D,Q)=\sum_{q_i \in Q} \text{IDF}(q_i)\cdot\frac{f(q_i,D)\cdot(k_1+1)}{f(q_i,D)+k_1\cdot\left(1-b+b\cdot\frac{|D|}{\text{avgdl}}\right)}$$

$$\text{IDF}(q_i)=\ln\left(1+\frac{N-n(q_i)+0.5}{n(q_i)+0.5}\right)$$

- $f(q_i,D)$ : 그 문서에 단어가 나온 횟수 — **많을수록 높다**
- $n(q_i)$ : 그 단어가 등장하는 문서 수 — **드물수록 높다**
- $|D|/\text{avgdl}$ : 문서 길이 / 평균 길이 — **짧을수록 높다**
- $k_1=1.2,\ b=0.75$ (Elasticsearch 기본값)

제목에는 2배 가중치를 준다. `fields: ["title^2.0", "text"]`

**실측 결과 (후보 50개):** 최고 `20.706` / 최저 `13.419`

| 순위 | 문서 | 점수 |
|---|---|---|
| 1 | ❌ 주간 업무 보고서 3/23~3/27 | **20.706** |
| 2 | ✅ 3년 근속 Refresh 휴가 제도 | 20.186 |
| 3 | ❌ talk-stock 2026-07 | 18.976 |
| 4 | ❌ 2026 Q2 피드백 | 18.607 |
| 5 | ❌ 회사 연차 규정이 궁금해요! | 18.571 |

정답이 2위다. 그런데 1위와 **0.52 차이**뿐이고, 1위와 5위의 차이도 **2.14**뿐이다.
다섯 건이 사실상 동점이며, **키워드 검색 스스로도 어느 것이 맞는지 모르고 있다.**

## ② kNN — 의미가 얼마나 가까운가

```
              q · d                              1 + cos(q, d)
cos(q, d) = ───────────        ES 점수 = ───────────────────────
             |q| × |d|                            2
```

$$\cos(\vec{q},\vec{d})=\frac{\vec{q}\cdot\vec{d}}{\|\vec{q}\|\,\|\vec{d}\|}
\qquad
\text{ES 점수}=\frac{1+\cos(\vec{q},\vec{d})}{2}$$

질문과 청크를 각각 1536차원 벡터로 만들어 각도를 잰다.
Elasticsearch는 음수를 피하려고 $(1+\cos)/2$로 변환해 저장하므로, 점수는 항상 0~1이다.

**실측 결과 (후보 50개):** 최고 `0.7440` / 최저 `0.6518`

| 순위 | 문서 | 점수 |
|---|---|---|
| 1 | ✅ 3년 근속 Refresh 휴가 제도 | **0.7440** |
| 2 | ❌ (협업 툴) Flex HR | 0.6820 |
| 3 | ❌ AI 풀스택 개발자 (8년 이상) | 0.6800 |
| 4 | ❌ 20260420_리더주간미팅 | 0.6730 |
| 5 | ❌ 2026-04-10 2주차 정기 미팅 | 0.6710 |

**단어가 겹치지 않는데도 정답을 1위로 올렸다.** "일한 사람이 쉬는 것"과
"근속 휴가 제도"가 같은 뜻이라는 것을 벡터가 알아본 것이다. 이것이 의미 검색을 넣은 이유다.

다만 1위와 5위 차이가 **0.073**뿐이다. 무관한 채용 공고가 거의 같은 점수를 받았다.
($(1+\cos)/2$를 역산하면 코사인 값은 0.30~0.49 구간이다. 애초에 좁은 범위에 몰려 있다.)

## ③ 결합 — RRF (Reciprocal Rank Fusion)

### 3-1. 무엇을 만드는가

두 검색이 각각 후보 청크 50개씩을 내놓는다. 어떤 청크는 양쪽에 다 들어 있고,
어떤 청크는 한쪽에만 들어 있다.

**이 청크들을 한 곳에 모아 중복을 없애고, 청크마다 새 점수를 하나씩 매긴다.**
새 점수는 그 청크가 **각 리스트에서 몇 등이었는지**로만 계산한다. 점수는 쓰지 않는다.

```
BM25 후보 50개 ┐
                ├→ 합집합 (중복 제거, 약 85~90개)
kNN  후보 50개 ┘         │
                          ▼
              청크마다  1/(60 + BM25순위) + 1/(60 + kNN순위)
                          │
                          ▼
                 새 점수로 전체 재정렬 → 단일 순위표
```

심사위원 둘이 **등수만** 매기고, 그 등수를 점수로 환산해 더한 뒤 줄을 세우는 것과 같다.

한쪽 후보 50개 안에 들지 못한 청크는 그쪽 기여가 0이다.
**더하기이므로 양쪽에 든 청크가 자연히 유리하다.**

### 3-2. 등수를 점수로 바꾸는 식

```
                  1
점수(등수) = ─────────────          k = 60
              k + 등수
```

| 등수 | 계산 | 값 |
|---|---|---|
| 1위 | `1 / (60 + 1)` | 0.016393 |
| 2위 | `1 / (60 + 2)` | 0.016129 |
| 5위 | `1 / (60 + 5)` | 0.015385 |
| 50위 | `1 / (60 + 50)` | 0.009091 |

**`k`를 더하는 이유** — `1/등수`로 하면 1위가 2위의 **두 배**라 너무 가파르다.
한 엔진에서 우연히 1등한 문서가 나머지를 압도해버린다.
`k=60`을 깔면 1위와 2위가 `0.016393` vs `0.016129`로 거의 같아져,
**여러 리스트에 골고루 든 문서가 이길 수 있게** 된다.

| `k` | 1위 | 50위 | 1위 ÷ 50위 |
|---|---|---|---|
| 10 | 0.09091 | 0.01667 | 5.45배 (상위권 강조) |
| **60** | 0.01639 | 0.00909 | **1.80배** (표준값) |
| 200 | 0.00498 | 0.00400 | 1.24배 (평평) |

### 3-3. 실제 계산 — 두 문서를 끝까지 따라가기

**문서 A · `주간 업무 보고서` (BM25 1위였던 오답)**

| 리스트 | 등수 | 계산 | 기여 |
|---|---|---|---|
| BM25 | **1위** | `1 / (60 + 1)` | **0.01639** |
| kNN | **후보 50개 밖** | — | **0.00000** |
| | | **합계** | **0.01639** |

**문서 B · `3년 근속 주기 Refresh 휴가 제도` (정답)**

| 리스트 | 등수 | 계산 | 기여 |
|---|---|---|---|
| BM25 | 11위 | `1 / (60 + 11)` | 0.01408 |
| kNN | **1위** | `1 / (60 + 1)` | **0.01639** |
| | | **합계** | **0.03048** |

> **BM25에서 1위였던 문서가 0.016, BM25 11위였던 정답이 0.030이 됐다.**
> 양쪽에 든 문서가 두 번 더해지기 때문이다.

**최종 상위 5건**

| 순위 | 점수 | BM25 | kNN | 문서 |
|---|---|---|---|---|
| 1 | **0.03048** | 11위 | **1위** | ✅ 3년 근속 Refresh 휴가 제도 |
| 2 | 0.02499 | 13위 | 32위 | ❌ 2026 Q2 피드백 |
| 3 | 0.02176 | 29위 | 35위 | ❌ 중소기업 청년소득세 감면 |
| 4 | 0.02175 | 34위 | 30위 | ❌ 건강검진(필수) |
| 5 | 0.01770 | **1위** | 밖 | ❌ 주간 업무 보고서 |

**양쪽에서 30등씩 한 문서가, 한쪽에서 1등인 문서보다 위에 온다.**
이것이 RRF의 성질이다. 두 검색이 동의한 것을 강하게 민다.

### 3-4. 왜 점수 대신 순위를 쓰는가

이전에는 각 리스트를 0~1로 정규화한 뒤 4:6으로 가중평균했다. 두 가지 문제가 있었다.

**① 폭이 좁은 리스트의 미세한 차이가 부풀려진다**

정규화는 점수를 "그 리스트의 전체 폭 대비 비율"로 바꾼다.

| | 1위 | 2위 | 전체 폭 | 실제 차이 | 정규화 후 |
|---|---|---|---|---|---|
| kNN | 0.7440 | 0.7060 | **0.0922** | 0.0380 | **0.4122** |

코사인 0.744와 0.706은 의미상 거의 같은데, 폭이 0.09밖에 안 되니 **0.038짜리 차이가
0.41로 부풀려진다.** kNN 후보는 늘 0.65~0.74의 좁은 구간에 몰려 있어 이 왜곡이 항상 일어난다.

**② 다른 문서들의 분포에 영향받는다**

`min`과 `max`가 바뀌면 **같은 문서의 점수가 바뀐다.**
색인이 커지면 BM25의 IDF가, 임베딩 모델을 바꾸면 코사인 분포가 이동한다.
실제로 코퍼스가 2,979 → 3,211청크로 늘면서 이전 발표 예시가 재현되지 않았다.

**순위는 다른 문서의 점수와 무관하다.** 1등은 언제나 1등이다.

RRF는 Elasticsearch, OpenSearch, Weaviate, Qdrant, Azure AI Search가 공통으로 쓰는 표준 방식이다.
(ES의 `retriever.rrf`는 유료 라이선스 기능이지만, 두 리스트를 이미 따로 받아
직접 합치고 있으므로 ES 기능 없이 계산할 수 있다.)

### 3-5. 트레이드오프

**RRF는 "압도적 1위"를 표현하지 못한다.** BM25가 완벽히 일치하는 문서를 찾아도
2위와 `0.00026` 차이일 뿐이다. 그 확신이 버려진다.

그래서 **질문에 문서 제목이 들어 있는 경우엔 이득이 없다.**

| 평가셋 | 이전 방식 hit@5 / MRR | RRF hit@5 / MRR |
|---|---|---|
| 제목 단어 84.7% 포함 | 0.974 / 0.908 | **0.974 / 0.908** (동일) |
| 제목 단어 6.4% | 0.658 / 0.527 | **0.763 / 0.560** |

키워드가 잘 맞으면 BM25 1위가 곧 정답이라 어느 방식이든 맞히고,
키워드가 어긋날 때 RRF가 낫다.

### 3-6. 가중치는 없앴다

RRF에도 가중치를 줄 수 있지만(`Σ w/(k+등수)`), 재보니 주지 않는 쪽이 나았다.

| | v4 hit@5 | v4 MRR |
|---|---|---|
| **동일 가중** | **0.763** | **0.549** |
| BM25 0.4 : kNN 0.6 | 0.737 | 0.531 |

이전의 `4:6`은 "kNN을 더 믿는다"는 뜻이면서 정규화 왜곡을 보정하는 성격도 있었다.
RRF에는 왜곡이 없으므로 가중치는 순수하게 "어느 엔진의 순위를 더 믿을까"가 되는데,
**그 답이 질문마다 달라** 고정 가중치가 오히려 방해가 된다.

## ④ 최신 문서 가산점

후보를 `updated_at` 기준 최신순으로 **5등분**하고, 최신 그룹부터 차등 가산합니다.
절대 시각이 아니라 **후보 풀 안에서의 상대 순위**로 나눕니다.

**값은 절대값이 아니라 "이론상 최대 결합 점수에 대한 비율"입니다.**

```
이론상 최대 = 2/(60+1) = 0.0328        (양쪽 리스트 모두 1위일 때)
RECENCY_BOOST_MAX = 0.04  →  최대 가산점 = 0.0328 × 0.04 = 0.0013
```

**왜 비율로 뒀나** — 결합 방식을 바꾸면 점수 범위가 통째로 달라집니다.
정규화 방식은 0~1이었고 RRF는 0~0.0328입니다.
절대값 0.04를 그대로 뒀다면 가산점이 점수를 압도해 **사실상 최신순 정렬**이 됐을 겁니다.

**비율별 실측**

| 가산점 | 제목 단어 있음 MRR | 제목 단어 없음 MRR |
|---|---|---|
| 끔 (0%) | 0.908 | 0.549 |
| **최대치의 4%** | **0.908** | **0.560** |
| 최대치의 10% | 0.846 | 0.496 |
| 최대치의 25% | **0.668** | 0.478 |

4%는 무해하거나 소폭 이득, 10%부터 떨어지고, 25%에서 무너집니다.

> 근거는 지표가 아니라 **"사내 문서에서 최신본을 우선하는 것이 타당한 기본 동작"**이라는 판단입니다.
> 관련도 상위는 흔들지 않고 동점 근처에서만 작동하도록 크기를 제한했습니다.

## ⑤ 청크가 아니라 "서로 다른 문서" 5건

같은 문서의 청크가 상위권을 독점하면 다른 관련 문서가 밀려난다.

> 실측 사례: MCP 문서 질문에서 상위 3건이 전부 "설치 방법" 청크로 채워지고,
> 정작 답이 있는 "기능 목록" 청크가 들어오지 못했다.

## ⑥ 문서 전문 확장

검색으로 문서가 한 번 걸리면 **그 문서의 청크를 `chunk_index` 순으로 이어붙여** 컨텍스트에 넣는다.
대표로 매칭된 청크 하나만 넣으면 정작 답이 있는 부분이 빠지기 때문이다.

문서마다 따로 조회하면 왕복이 `top_k`에 비례해 늘어나므로(N+1),
`terms` 쿼리 **하나**로 다 가져와 파이썬에서 `doc_id`별로 나눈다.

## 최종 결과

| 순위 | BM25 단독 | kNN 단독 | **하이브리드** |
|---|---|---|---|
| 1 | ❌ 주간 업무 보고서 `20.71` | ✅ 정답 `0.744` | ✅ **정답 `0.971`** |
| 2 | ✅ 정답 `20.19` | ❌ Flex HR `0.682` | ❌ 주간 업무 보고서 `0.440` |
| 3 | ❌ talk-stock `18.98` | ❌ 채용 공고 `0.680` | ❌ talk-stock `0.345` |
| 4 | ❌ Q2 피드백 `18.61` | ❌ 리더주간미팅 `0.673` | ❌ Q2 피드백 `0.328` |
| 5 | ❌ 연차 규정 `18.57` | ❌ 정기 미팅 `0.671` | ❌ AI/LLM 브리핑 `0.306` |
| **1~5위 점수 차** | 2.14 | **0.073** | **0.665** |
| **1위와 2위 차** | 0.52 | 0.062 | **0.531** |

> **"정답이 1위"인 것보다 "1위가 확실히 1위"인 것이 중요하다.**
> 순위를 믿을 수 있어야 상위 5건만 잘라서 LLM에 넘길 수 있다.

## 평가 — 측정 도구를 먼저 의심했다

검색 지표는 정답 문서 ID만 있으면 계산되므로 LLM 판정 없이 잰다.

| 지표 | 정의 |
|---|---|
| `hit@5` | 정답 문서가 상위 5건 안에 들었는가 (0 또는 1) |
| `MRR` | $1/\text{정답 순위}$ — 1위 `1.0` / 2위 `0.5` / 3위 `0.33` / 못 찾음 `0` |

45문항 중 **38문항**을 채점한다. 본문 없는 문서를 겨냥한 문항과 사내 문서에 없는 질문은
검색이 못 찾는 것이 정상이라 제외한다.

### 발견: 평가셋이 키워드 검색에 유리하게 기울어 있었다

평가셋을 만들 때 쓴 프롬프트에 이런 지시가 있었다.

> *"문서 제목, 상위 경로, 팀명, 프로젝트명, 날짜 등 이 문서를 고유하게 식별할 수 있는
> 구체적인 단서 키워드를 질문 안에 반드시 자연스럽게 포함하세요"*

질문이 채점 불가능해지는 것을 막으려는 의도였고 그 목적에는 맞다. 부작용이 있었다.

| | 값 |
|---|---|
| 제목 단어가 질문에 **100% 포함**된 문항 | **27 / 38 (71%)** |
| 절반 이상 포함 | 34 / 38 |
| 평균 포함률 | **84.7%** |

**대부분의 문항이 "제목을 알려줄 테니 그 문서를 찾아라"를 묻고 있었다.**

### 대응: 같은 정답 문서, 제목 단어만 뺀 대조 평가셋

38문항을 **같은 정답 문서를 겨냥한 채로** 다시 썼다. 제목·경로·팀명을 쓰지 말고
동의어와 구어체로 묻게 해서 제목 단어 누출을 **84.7% → 6.4%**로 낮췄다.
정답 문서를 고정했으므로 **질문 표현 외의 변수는 통제된다.**

| | 원래 질문 | 다시 쓴 질문 |
|---|---|---|
| 예시 1 | LLOYDK 솔루션/개발 경로의 **'정보처리기사 자격증 취득현황'** 문서에서 자격증 파일 업로드 방법은? | 자격증 파일을 어떻게 올리면 되나요? |
| 예시 2 | LLOYDK의 **'종합건강검진 제도'** 문서에 따르면 2026년부터 시행되는 연 1회 종합검진 제도는? | 2026년부터 시작되는 연 1회 건강검진은 어떻게 진행되나요? |

### 측정 결과

| 방식 | 제목 단어 있음 hit@5 / MRR | 제목 단어 없음 hit@5 / MRR | MRR 낙폭 |
|---|---|---|---|
| BM25 단독 | 0.947 / 0.864 | 0.605 / 0.390 | **−55%** |
| **하이브리드 (RRF)** | **0.974 / 0.908** | **0.763 / 0.560** | **−38%** |
| kNN 단독 | 0.921 / 0.812 | 0.605 / 0.501 | −38% |
| (참고) 이전 min-max 4:6 | 0.974 / 0.908 | 0.658 / 0.527 | −42% |

문항별 직접 대결 (하이브리드 vs BM25 단독, MRR 기준)

| | 하이브리드 승 | BM25 승 | 동점 |
|---|---|---|---|
| 제목 단어 있음 | 5 | 3 | 30 |
| 제목 단어 없음 | **16** | 2 | 20 |

> **결론: BM25는 조건이 맞으면 강하지만 어긋나면 절반 아래로 떨어진다.
> 하이브리드의 값어치는 최고점이 아니라, 질문이 어떻게 들어와도 덜 무너지는 데 있다.
> 사용자의 말투를 통제할 수 없는 사내 챗봇에서는 이 성질이 더 중요하다.**

### 채택하지 않은 것: 슬롯 배분

"kNN에서 3건 + BM25에서 2건"처럼 **점수를 섞지 않고 자리를 나눠 갖는** 방식도 측정했다.
한쪽에만 걸린 문서도 자리가 보장되므로 "한쪽 기여가 0" 성질을 피할 수 있다.

| 문항 집합 | 하이브리드 MRR | 슬롯(kNN3+BM25 2) MRR |
|---|---|---|
| 제목 단어 있음 | **0.908** | 0.827 |
| 제목 단어 없음 | **0.560** | 0.525 |

min-max 정규화를 쓰던 시절에는 제목 단어 없는 질문에서 슬롯이 근소하게 앞섰으나,
**RRF로 바꾼 뒤로는 양쪽 모두에서 하이브리드가 앞선다**(+0.081, +0.035).
또한 슬롯은 질문과 무관하게 자리를 고정하므로, 질문마다 어느 검색이 더 확신을 갖는지
반영하지 못한다.

### 한계 (반드시 함께 말할 것)

- 38문항 1회 측정이다. **±0.02 수준의 차이는 노이즈와 구분되지 않는다.**
- 대조 평가셋은 제목 단서를 빼면서 일부 문항이 모호해졌다(정답 문서가 유일하지 않을 수 있음).
  절대 수치는 과소평가되며 **방식 간 비교에만 쓴다.**
- 대조 평가셋의 문장은 LLM이 다시 쓴 것이다. "제목을 모르고 묻는 경우"를 대신할 뿐
  실사용 질문 분포를 대표하지 않는다.

# 슬라이드 3 · 증분·삭제 처리

## 한 줄 메시지

> **재색인 비용의 대부분은 임베딩 API 호출이다. 바뀐 것만 다시 넣는다.**

## 전체 흐름

```
Confluence 문서 640건
   │
   ├─① 건너뛰기 ──── updated_at 비교 → 바뀐 문서만 남긴다
   │                    (변화 없으면 임베딩 호출 0회)
   ├─② 지우고 쓰기 ── 대상 문서의 기존 청크를 먼저 삭제 → 새로 색인
   │
   └─③ 삭제 동기화 ── Confluence에서 사라진 문서를 색인에서도 제거
   │
Elasticsearch  583문서 / 3,211청크
```

## ① 건너뛰기 — 비용을 지킨다

```python
indexed_updated_ats = get_indexed_updated_ats(doc_ids)
target_pages = [p for p in pages
                if indexed_updated_ats.get(p["id"]) != p.get("last_updated")]
```

**세 가지 경우가 나온다.**

1. **값이 같다** — 문서가 그대로다 → 건너뛴다
2. **값이 다르다** — 문서가 수정됐다 → 다시 색인한다
3. **ES에 값이 없다** — 처음 보는 문서다 → 색인한다

| doc_id | 문서 | ES에 저장된 값 | Confluence 최신 값 | 판정 |
|---|---|---|---|---|
| `21102704` | 주차 지원 기준 | `2026-09-02T02:16:51.205Z` | `2026-09-02T02:16:51.205Z` | ① 같음 → **건너뜀** |
| `105021485` | 3년 근속 Refresh 휴가 제도 | `2025-12-19T07:14:31.318Z` | (그 이후 수정됐다면) | ② 다름 → **재색인** |
| `(신규 문서)` | 어제 새로 만든 문서 | 없음 | 있음 | ③ 신규 → **재색인** |

> ES 열의 값은 실측이다. Confluence 열은 세 경우를 한 표에 보이려고 상황을 가정했다.

문자열을 그대로 비교한다. ES 집계가 돌려주는 형식과 Confluence가 주는 형식이
같다는 것을 확인했다(`2026-09-02T02:16:51.205Z`). **형식이 어긋나면 모든 문서가
매번 바뀐 것으로 판정되어 조용히 전체 재색인이 돈다.** 매핑이나 API 응답 형식을
바꿀 때 확인이 필요한 지점이다.

`--force`를 주면 비교를 건너뛰고 전부 재색인한다.

### 집계(aggregation)를 쓴 이유

한 문서는 여러 청크로 쪼개져 있지만 `updated_at`은 **문서 단위로 동일**하다.
`doc_id`로 묶어 대표값 하나씩만 가져오면 된다.

```python
{
  "size": 0,                                   # 본문은 아예 받지 않는다
  "query": {"terms": {"doc_id": doc_ids}},
  "aggs": {"by_doc": {
      "terms": {"field": "doc_id", "size": len(doc_ids)},
      "aggs": {"latest_updated_at": {"max": {"field": "updated_at"}}}
  }}
}
```

> 이것이 아끼는 것은 Elasticsearch 조회가 아니라 **임베딩 API 호출**이다.
> 문서 583건을 전부 다시 임베딩하는 것과 바뀐 3건만 하는 것의 차이다.

## ② 지우고 쓰기 — 정합성을 지킨다

`chunk_id`를 `_id`로 쓰므로 같은 청크는 자동으로 덮어쓰기된다.
**그런데 그것만으로는 부족하다.**

```
문서 수정 전:  chunk_0   chunk_1   chunk_2   chunk_3   chunk_4
문서가 짧아짐:  chunk_0   chunk_1   chunk_2
               └──── 덮어쓰기 ────┘   ↑ chunk_3, chunk_4는 덮어쓸 대상이 없다
                                       → 이전 버전 내용이 그대로 남는다 (고아 청크)
```

그래서 색인 **전에** 해당 문서의 청크를 전부 지운다.

```python
delete_documents_by_ids(target_doc_ids)      # 먼저 삭제
...
index_document_chunks(all_chunks, vectors)   # 그 다음 색인
```

> 이 패턴은 이전 프로젝트(`pre/`)에서 같은 문제를 겪고 가져온 것이다.

## ③ 삭제 동기화

Confluence에서 문서가 삭제돼도 색인에 남아 있으면 **챗봇이 이미 없는 문서를 근거로 답한다.**
두 목록을 비교해 색인에만 있는 문서를 지운다.

```
Confluence에 있는 문서 id   ─┐
                              ├→ 색인에만 있는 것 = 삭제된 것 → 제거
색인에 있는 doc_id          ─┘
```

**실측 (2026-09-14)**

| | 건수 | |
|---|---|---|
| Confluence 전체 | 651 | |
| 색인 | 583 | |
| Confluence에만 있음 | 68 | 본문 없는 문서 57 + 새로 생긴 11 |
| **색인에만 있음** | **0** | 삭제된 문서 없음 |

### 안전장치 세 가지

검색 데이터를 지우는 동작이라 잘못 돌면 되돌리기 어렵다.

| 장치 | 막는 사고 |
|---|---|
| **전체 스페이스 실행에서만 동작** | `--limit 10`으로 10건만 수집한 상태로 비교하면 **나머지 573건이 전부 삭제 대상**이 된다 |
| **id 수집 실패 시 예외를 올림** | 기존에는 예외를 삼키고 부분 목록을 돌려줬다. 절반만 받아오면 나머지 절반을 삭제한다 |
| **목록이 비면 건너뜀** | 빈 목록은 "전부 삭제"를 뜻하게 된다 |

`--no-prune`으로 이 단계만 끌 수 있다.

## 덤: 무중단 전체 재색인

일상적인 증분 색인과 별개로, 모델이나 분석기가 바뀌어 **전체 재구축**이 필요할 때의 경로다.

```
[confluence-current] ──현재──> confluence-openai-v2
                                       │
                     ① 새 인덱스 v3 생성 (바뀐 매핑)
                     ② _reindex로 복사
                     ③ 별칭만 옮긴다  ← 이 순간만 전환, 검색은 안 끊김
                                       │
[confluence-current] ──전환──> confluence-openai-v3
```

**실제로 이번 프로젝트에서 두 번 사용했다.**

| | |
|---|---|
| 소요 시간 | **8초** (3,211건, 실패 0건) |
| 임베딩 API 호출 | **0회** — `_reindex`가 기존 `text_vector`를 그대로 복사 |
| 롤백 | 별칭을 되돌리는 것 하나 |

별칭이 없으면 같은 작업에 `.env` 수정과 컨테이너 재생성이 필요하고, 그 사이 검색이 멈춘다.
