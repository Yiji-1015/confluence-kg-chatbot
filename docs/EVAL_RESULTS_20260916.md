## 1. 평가셋의 출처와 한계 (먼저 읽을 것)

**두 평가셋 모두 사람이 손으로 쓴 것이 아니다.**

| 평가셋 | 만든 주체 | 방법 |
|---|---|---|
| v2 (45문항) | GPT-4o | `generate_dataset.py` — ES에서 카테고리별 대표 문서를 뽑아 자동 생성 |
| 55문항 중 50 | 별도 도구 | |
| 55문항 중 5 (`attachment`) | 수작업 | 색인에서 실제 문서·첨부명을 확인해 작성 |

이후 실패 문항을 열어보며 라벨 오류를 수정한 기록이 있다(CHANGELOG 2026-09-01 항목:
지표 적용 오류 2건, 데이터셋 라벨 오류 1건). **"자동 생성 후 검증·수정"이 정확한 표현이며,
"수동 검증 평가셋"이라고 하면 과장이다.**

**v2에는 구조적 편향이 있다.** 생성 프롬프트가 "문서를 고유하게 식별할 수 있는 단서
키워드를 질문에 반드시 포함하라"고 지시했다. 그 결과 채점 문항 38개 중 27개(71%)가 문서
제목 단어를 100% 포함하고, 평균 누출률이 84.7%다. **BM25에 유리한 조건이다.**

**평가셋 B는 19문항을 채점할 수 없다.** 정답 문서가 색인에 없기 때문이다.

| 실제 스페이스 | 이름 | 문서 |
|---|---|---|
| `ILA` | `[IN] LLOYDK AX` | AX Workspace - 09, 10 |
| `aHBUQwIEKwUG` | `기술연구소` | UI/UX 결정사항, DO-Parse·DO-SPE 기능 리스트 |
| `segM5ic0oN9L` | `솔루션개발팀` | KDO-06. 설치 및 배포 가이드 |

수집 대상은 키가 `LLOYDK`인 스페이스 하나뿐이다. `ILA`는 **이름**에 LLOYDK가 들어 있어
같은 스페이스로 오해하기 쉽다. 남은 33문항은 정답 문서가 18종에 몰려 있고(상위 5문서가
51.5%), `table` 축이 2문항뿐이다. **축별 수치는 방향 지표로만 쓴다.**

## 2. 표 ① 검색 방식 비교

### 2-1. v2 (38문항, 정답 문서 38종)

| 방식 | hit@5 | MRR |
|---|---|---|
| 하이브리드 RRF (운영) | 0.974 | 0.890 |
| 이전 방식 min-max 4:6 | 0.974 | **0.895** |
| BM25 단독 | 0.947 | 0.864 |
| kNN 단독 | 0.895 | 0.786 |

**네 방식이 사실상 갈리지 않는다.** `hit@5`는 0.895~0.974, `MRR`은 0.786~0.895 안에 모여
있고, RRF와 min-max의 차이는 0.005(38문항 중 1문항 미만)다. 문항별 승부도 하이브리드 5승 /
BM25 4승 / 동점 29다.

**이 표만으로는 하이브리드·RRF를 쓸 근거가 나오지 않는다.** 제목 단어 누출률 84.7%라는
조건 때문이며, 평가셋의 성질이지 검색의 성질이 아니다.

### 2-2. 평가셋 B (33문항)

| 방식 | hit@5 | MRR |
|---|---|---|
| **RRF (운영)** | **0.818** | 0.553 |
| min-max 4:6 | 0.697 | 0.477 |
| BM25 단독 | 0.697 | **0.563** |
| kNN 단독 | 0.576 | 0.388 |

`hit@5`는 RRF가 0.818로 가장 높다(min-max 대비 +0.121, 4문항). `MRR`은 BM25 단독이
0.563으로 근소하게 앞서며 33문항 기준 1문항 차이라 노이즈 범위다.

## 3. 표 ② 카테고리별 (평가셋 B, 각 칸 hit@5 / MRR)

v2에는 카테고리 축이 없어 평가셋 B로만 측정했다.

| 축 | n | RRF | min-max | BM25 | kNN |
|---|---|---|---|---|---|
| keyword | 7 | 0.86 / 0.61 | 0.86 / 0.60 | 0.86 / 0.62 | 0.71 / 0.46 |
| semantic | 8 | **0.75** / 0.49 | 0.62 / 0.34 | 0.62 / 0.56 | 0.62 / 0.32 |
| conversational | 6 | **0.83 / 0.49** | 0.67 / 0.47 | 0.50 / 0.29 | 0.33 / 0.33 |
| table | 2 | 1.00 / 1.00 | 1.00 / 1.00 | 1.00 / 0.75 | 1.00 / 0.75 |
| boundary | 5 | **0.80** / 0.36 | 0.40 / 0.17 | 0.60 / 0.50 | 0.20 / 0.07 |
| attachment | 5 | 0.80 / 0.67 | 0.80 / 0.64 | 0.80 / **0.80** | 0.80 / 0.64 |

**읽을 수 있는 것은 두 가지뿐이다.**

- `keyword`에서는 네 방식이 동률(0.86)이다. 키워드가 그대로 있으면 BM25로 충분하다.
- `conversational`에서 BM25가 0.50으로 가장 약하고 RRF가 0.83으로 가장 강하다.
  구어체는 원문 표현과 멀어져 키워드 검색이 잘 듣지 않는다. **현재 확보한 근거 중
  하이브리드를 정당화하는 가장 직접적인 수치다.** 다만 6문항 / 4문서다.

`table`은 2문항이라 판단 불가. `attachment`에서 BM25 `MRR`이 가장 높은 것은 파일명이
키워드 그 자체이기 때문이며 자연스럽다.

## 4. 표 ③ RRF가 실제로 바꾼 문항

| | v2 (38문항) | 평가셋 B (33문항) |
|---|---|---|
| RRF만 찾음 | **0** | **5** |
| RRF만 놓침 | **0** | **1** |
| 순위 상승 | 1 | 5 |
| 순위 하락 | 2 | 4 |
| 둘 다 실패 | 1 | 5 |

**v2에서는 RRF가 1문항 손해다**(상승 1 / 하락 2, top5 진입 변화 0). min-max `MRR`이 0.895로
근소하게 높았던 이유가 이것이다.

**평가셋 B에서는 순증 4문항이다.** `hit@5` 0.697 → 0.818의 실체다.

```
id12 [semantic]  min-max 실패 -> RRF 3위 | 가짜 답변을 먼저 만들어서 벡터 검색 정확도 높이는 기법
id16 [conver]    min-max 실패 -> RRF 5위 | 회의록은 비공개로 만들어도 되는 거야?
id34 [semantic]  min-max 실패 -> RRF 4위 | 이해충돌 가능성이 생기면 회사에서는 어떻게 처리해?
id42 [boundary]  min-max 실패 -> RRF 3위 | 협력사에서 받는 금품이나 편의는 받아도 돼?
id43 [boundary]  min-max 실패 -> RRF 5위 | 익명 신고했다는 이유로 불이익 줄 수 있어?
```

세 번째부터는 문서 제목 단어가 없는 질문이다. BM25 점수가 낮아 min-max에서는 정규화해도
kNN 점수에 눌려 사라지지만, RRF는 점수가 아니라 **순위**만 쓰므로 "kNN 리스트 3위" 같은
기여가 살아남는다.

**둘 다 실패한 문항**은 검색 방식 문제가 아닌 경우가 많다.

```
id4  로이드케이의 핵심가치 Core Value 3가지
id13 지식베이스 만들고 파일 올리면 어떤 과정 거쳐서 인덱싱돼?
id26 DO-MINE에서 음성 파일(STT) 전처리 모듈 설정 방법은?   <- 문서에 답이 없는 unsupported 문항
id52 ESG 경영 방침 문서 있어?                            <- BM25 단독으로는 1위, 결합에서 밀림
```

## 5. Nori 분석기 개선 A/B

개선 전 설정으로 별도 인덱스(`confluence-oldnori-ab`)를 만들어 비교했다. `_reindex`는
`text_vector`를 그대로 복사하고 `text`만 대상 인덱스의 분석기로 재분석하므로 임베딩 비용이
들지 않는다 (3,493건 / 실패 0).

| | 개선 전 | 현재 |
|---|---|---|
| tokenizer | `nori_tokenizer` (decompound 기본=discard) | `ko_nori_tokenizer` (decompound=**mixed**) |
| filter | 없음 | `ko_pos_filter` + `lowercase` |

```
HashiCorp 자격증   개선 전 ['HashiCorp','자격','증']  ->  현재 ['hashicorp','자격증','자격','증']
BlackBird         개선 전 ['BlackBird']            ->  현재 ['blackbird']
```

### 결과 — 현재 평가셋으로는 개선이 확인되지 않는다

| 평가셋 | 지표 | 개선 전 | 현재 |
|---|---|---|---|
| **v2** | BM25 hit@5 / MRR | **0.974 / 0.921** | 0.947 / 0.864 |
| | 하이브리드 hit@5 / MRR | **0.974 / 0.921** | 0.974 / 0.890 |
| **평가셋 B** | BM25 hit@5 / MRR | **0.727** / 0.557 | 0.697 / **0.563** |
| | 하이브리드 hit@5 / MRR | 0.788 / **0.575** | **0.818** / 0.553 |

**v2에서는 명확히 손해다.** BM25 순위 변동 3건이 전부 악화다. 제목 단어가 그대로 있는
질문에서는 원형 토큰(`HashiCorp`, `BlackBird`)이 오히려 유리하기 때문이다.

**평가셋 B에서는 변동 5건에 개선 3 / 악화 2로 사실상 무승부다.**

> **발표 판단**: 현재 확보한 두 평가셋 어느 쪽으로도 Nori 개선의 이득을 보일 수 없다.
> **5페이지 본문에서 "Nori를 개선했다"고 주장하면 근거 없이 말하는 것이 된다.**
> 질문받으면 전후 수치를 제시해야 하는데, 그 수치가 개선을 보여주지 않는다.
> 이 항목은 본문에서 빼고, 필요하면 "한국어 형태소 분석기를 튜닝했고 효과는
> 현재 평가셋에서 확인되지 않았다"는 사실 서술로만 남긴다.

## 6. 운영 지표 (실서비스 경로 측정)

`run_qa.py`는 `search_hybrid` / `generate_answer`를 직접 호출해 API를 우회하므로 Prometheus에
아무것도 남지 않는다. 단계별 계측(`stage()`)이 `api/v1/chat.py`에만 있기 때문이다.

이번에는 Spring Boot가 호출하는 것과 같은 경로(`POST /internal/chat`)로 52문항을 실행했다.
실행 직전·직후의 `/metrics`를 떠서 **이번 실행분만** 분리했다.

**성공 52 / 실패 0 / 총 159.3초**

| 단계 | 건수 | 평균 |
|---|---|---|
| `embedding` | 52 | 0.376s |
| `search` | 52 | 0.098s |
| `context_build` | 52 | ~0.000s |
| `generation` | 52 | **2.585s** |
| 전체 요청 | 52 | 3.06s (p95 5.32s) |

**생성이 전체 지연의 84%다. 검색은 0.1초로 병목이 아니다.**

> p50/p95는 히스토그램 버킷 경계(0.05·0.1·0.25·0.5·1·2·5·10·20·30·60)로 반올림되므로
> 정밀하지 않다. **평균을 기준 수치로 쓴다.**

## 7. 한계 — v4 대조군 제거의 영향

2026-09-16에 v4 paraphrase 대조군(`paraphrase_dataset_items.py`)과 그 생성기를 삭제했다.
GPT-4o가 GPT-4o의 질문을 재작성한 것이라 "실제 사용자 질문의 표본"으로 제시하기 어렵다고
판단했기 때문이다.

**그 결과 다음 주장의 근거가 사라졌다. 발표에서 말할 수 없다.**

- BM25가 제목 단어 없는 질문에서 무너진다 (−55%)
- 하이브리드가 그 조건에서 버틴다
- RRF가 min-max보다 낫다 (v2에서는 오히려 min-max가 근소 우위)
- Nori 개선에 효과가 있다 (v2에서는 손해)

**현재 남은 근거는 평가셋 B의 `conversational` 축 하나뿐이다** (BM25 0.50 vs RRF 0.83,
6문항 / 4문서). 표본이 작아 단독으로 강하게 주장하기 어렵다.

**되돌리려면** 삭제한 v4를 git 이력에서 복구하거나(`git show <commit>:<path>`),
제목 단어를 쓰지 않는 질문을 사람이 직접 작성해 새 대조군을 만들어야 한다.
후자가 방법론적으로 더 튼튼하다.

## 8. 정리

- v2만으로는 네 검색 방식이 갈리지 않는다. 평가셋의 제목 단어 누출률 84.7% 때문이다.
- 평가셋 B에서는 RRF가 `hit@5` 0.697 → 0.818로 앞선다. 순증 4문항이 실체다.
- 구어체 질문에서 BM25 단독이 가장 약하고(0.50) RRF가 가장 강하다(0.83).
- Nori 개선은 현재 평가셋으로 이득을 보일 수 없다. 5페이지 본문에서 빼는 것이 맞다.
- 생성이 지연의 84%이며 검색은 병목이 아니다.

## 9. 남은 일

- 평가셋 B의 19문항을 LLOYDK 문서로 교체하면 55문항 전체를 쓸 수 있다. `table` 축도 복구된다.
- 제목 단어를 쓰지 않는 대조군을 사람이 직접 작성하면 4·5페이지의 근거가 복구된다.
- 비교용 인덱스 `confluence-oldnori-ab`(3,493건)는 지우지 않았다. 재현이 끝나면 삭제해도 된다.
- 09-14 확정값은 583문서·3,211청크 기준이라 현재와 다르다. 발표 수치는 이 문서로 통일한다.
