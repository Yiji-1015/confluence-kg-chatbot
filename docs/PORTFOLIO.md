# Confluence RAG Chatbot 포트폴리오

## 문제

사내 Confluence 문서는 양이 많고 계층이 깊어 키워드만으로 필요한 근거를 찾기 어렵다. 답변 모델만 연결하면 출처 없는 추측도 발생한다.

## 해결

- Nori BM25로 한국어 키워드 일치 검색
- OpenAI 임베딩 기반 kNN 의미 검색
- BM25와 kNN의 순위를 RRF로 결합 (점수 범위가 달라 정규화 가중합은 폐기)
- 상위 청크가 아닌 서로 다른 상위 문서를 선택
- 선택 문서의 청크를 순서대로 합쳐 답변 근거 구성
- 답변과 함께 원본 Confluence URL 반환

## 주요 구현

| 영역 | 구현 |
|---|---|
| 수집 | 페이지네이션, 카테고리 경로, 수정일 기준 증분 재색인, 재색인 시 고아 청크 정리 |
| 파싱 | Confluence 매크로 정제, 링크 텍스트 보존, 표 변환, 청킹 |
| 검색 | BM25 · kNN 순위를 RRF(K=60)로 결합, 문서 단위 중복 제거 후 전문 확장 |
| 모델 | LiteLLM 게이트웨이, 질문 길이 기반 모델 라우팅, 장애 시 폴백 |
| 프레임워크 | 청킹에 `langchain-text-splitters`만 사용. 검색·프롬프트·평가는 직접 구현 |
| 세션 | PostgreSQL 영속화, Redis 최근 5턴 캐시 |
| 관측 | Langfuse trace, latency, token, cost 기록 |
| 평가 | 45문항 골든셋, 6개 지표(검색 2 + 생성 2 + RAGAS 2), 실패 원인 자동 분류 |
| 배포 | 역할별 Docker Compose 분리와 리소스 제한 |

## 측정 결과 (2026-09-14)

583문서 · 3,211청크 / 검색 38문항 · 생성 45문항 / 판정 모델 `solar`

| 지표 | 값 |
|---|---|
| `retrieval_hit@5` | 0.974 |
| `retrieval_mrr` | 0.908 |
| `answer_faithfulness` (직접 구현) | 0.973 |
| `ragas_faithfulness` (표준) | 0.856 |
| `answer_correctness` | 0.958 |
| `ragas_context_precision` | 0.851 |

여섯 지표가 모두 45문항 전부 채점된 첫 실행이다. 이전 측정값은 판정 모델의 출력 한도
때문에 일부 문항이 빠진 평균이었다(`docs/EVALUATION.md` 5.2절).

세 점수를 조합하면 오답 원인을 검색 실패 / 컨텍스트 무시 / 이해 실패로 분리할 수 있다.
기준선(09-01)의 실패 3건을 직접 열어보니 2건은 지표 적용 오류(본문 없는 문서를 검색
지표로 채점), 1건은 데이터셋 라벨 오류(실제로 존재하는 문서를 out-of-domain으로 표기)로
지표 자체의 문제였고 모두 해소했다. 현재 남은 실패는 1건(`qa-v2-021`)이며, 질문이 문서를
특정하지 못하는 건이라 한 문항에 맞춰 전역 스코어링을 바꾸지 않고 유지하고 있다.

자체 구현 faithfulness와 RAGAS 표준 지표를 나란히 기록해 교차 검증했고,
자체 지표가 0.11~0.12 후하게 채점한다는 것을 확인했다(09-01 0.113 → 09-14 0.117).
결합 방식과 분석기를 여러 번 바꾸는 동안 격차가 일정해, 우연이 아니라 판정 방식 차이에서
오는 구조적 편향이다. RAGAS는 답변을 문장 단위로 쪼개 각각 판정하는 반면 자체 구현은
답변 전체를 한 번에 보기 때문이다.

최신 문서 가산점은 검색 지표를 바꾸지 않았고 `context_precision`만 0.035 낮췄다
(09-02, min-max 시절 측정). 관련성이 아닌 최신성으로 문서를 올리는 대가이며, 이득이
측정되지 않았음을 알고도 "최신본 우선"이라는 제품 판단으로 유지하고 있다. RRF 전환 후
가산점을 비율(최대 결합 점수의 4%) 방식으로 바꿔 재측정했고, 10%부터 지표가 무너진다.

## 검증 기준

- 전체 Confluence 문서가 누락 없이 수집되는지 확인
- 변경 문서만 재색인되는지 확인
- BM25와 kNN 검색 결과 및 결합 점수 비교
- 멀티턴 질문에서 최근 대화가 반영되는지 확인
- 답변 출처가 실제 검색 문서와 일치하는지 확인

## 알려진 한계

- 검색 실패 1건은 질문이 문서를 특정하지 못한다(같은 날짜 회의록 5건). Nori가
  `20260303`을 단일 토큰으로 잘라 `2026년 3월 3일`과 겹치지 않는 것이 근본 원인이며,
  `multi_match`의 `best_fields`가 최고 필드 점수만 채택해 날짜 필드 기여분이 버려진다.
- 필드 결합 방식 3종(best_fields / tie_breaker / most_fields)을 비교했으나
  `hit@5`로는 구분되지 않았고 MRR로만 갈렸다. 표본 38건에서 1~2건 차이라 확정하지 않고
  현재 방식을 유지했다.
- 벡터 검색은 HNSW 근사에 int8 양자화가 적용된 상태다. 3,211청크 규모에서는
  정확 검색으로도 충분해 근사의 이득이 없다.
- 멀티턴 검색은 직전 사용자 발화를 검색어에 붙이는 방식이라 주제 전환에 약하다.
  LLM 질의 재작성이 정석이나 호출과 지연이 늘어 먼저 싼 쪽을 택했다.
