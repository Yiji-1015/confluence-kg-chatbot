## 2. 검색 전 과정

```text
검색용 질문 + 질문 벡터
 → BM25 최대 50청크 조회
 → kNN 최대 50청크 조회
 → chunk_id로 합치고 RRF 점수 계산
 → 수정일 가산점 추가
 → 점수 내림차순 정렬
 → doc_id 중복을 건너뛰며 최대 5문서 선택
 → 선택 문서의 청크 일괄 재조회
 → 순서대로 이어붙인 본문 반환
```

BM25와 kNN 조회는 현재 함수 안에서 순차 실행한다. `search_hybrid_async()`는 이 동기 함수 전체를 `asyncio.to_thread()`로 옮긴다. 두 검색을 동시에 실행한다는 뜻은 아니다.

## 3. BM25: 어떤 단어가 어디에 등장하는가

직관적으로 BM25는 질문 단어가 많이 등장하면 가산하되 무한히 비례시키지 않고, 많은 청크에 흔하게 있는 단어보다 드문 단어를 더 중요하게 본다. 길이가 긴 텍스트가 단순히 단어가 많다는 이유로 유리해지는 것도 보정한다.

이 프로젝트에서 ES의 검색 문서 단위는 청크다. 따라서 단어 빈도·길이 통계도 청크 색인의 영향을 받는다.

실제 쿼리는 `multi_match`의 `fields=["title^2.0", "text"]`, `type="best_fields"`다. 제목 필드 매칭에 2배 boost를 주고, 두 필드 중 가장 높은 필드 점수를 중심으로 평가한다. 제목과 본문 점수를 언제나 단순 합산하는 구조는 아니다.

Nori 품사 필터는 조사·어미 등이 점수를 지배하지 않게 한다. 문서에 거의 없는 구어체 어미가 질문에 등장하면, 희소성만으로 높은 가중치를 받을 수 있기 때문이다. 실제 조사 사례와 수치는 [RETRIEVAL.md](../RETRIEVAL.md)에 기록돼 있다.

## 4. kNN: 의미 표현이 가까운 청크 찾기

질문 벡터와 저장된 text_vector를 사용한다. 같은 단어가 없더라도 비슷한 의미의 문단을 후보로 가져오려는 경로다. 예를 들어 직원의 “오래 일한 사람의 쉬는 날”과 문서의 “근속 휴가”처럼 표현이 다른 경우다.

| 값 | 기본값 | 구분 |
|---|---:|---|
| RETRIEVAL_CANDIDATE_SIZE | 50 | BM25와 kNN이 각각 반환하는 후보 청크 수 |
| kNN k / size | 50 / 50 | kNN 결과로 요청하는 개수 |
| kNN num_candidates | 250 | `max(candidate_size × 5, 50)`으로 지정한 탐색 후보 설정 |
| RETRIEVAL_TOP_K | 5 | 최종 서로 다른 원본 문서 수 |

250, 50, 5는 서로 다른 단계의 숫자다. 원시 유사도 점수는 정답 확률이 아니다. 점수 차가 작다는 사실만으로 두 결과가 의미상 동일하거나 검색이 무의미하다고 결론내릴 수도 없다.

`space_key` 인수가 있으면 두 검색 모두 필터를 적용한다. 현재 채팅 엔드포인트는 이 인수를 전달하지 않는다. 이 필터 지원이 사용자별 문서 접근 권한 구현을 의미하지는 않는다.

## 5. RRF: 점수 대신 순위 합치기

`_rrf_scores()`가 각 목록을 `chunk_id → 1/(K+rank)`로 바꾼다. rank는 1부터, K 기본값은 60이다.

```text
score(chunk) = BM25 목록 기여 + kNN 목록 기여
목록에 없으면 그쪽 기여 = 0
```

| 예시 청크 | BM25 | kNN | RRF 점수 |
|---|---:|---:|---:|
| A | 1위 | 후보 밖 | 1/61 ≈ 0.01639 |
| B | 10위 | 10위 | 2/70 ≈ 0.02857 |
| C | 1위 | 1위 | 2/61 ≈ 0.03279 |

B가 A보다 높다. 두 목록에서 함께 발견되는 청크를 선호하는 성질이다. 같은 원본 문서라도 BM25가 청크 0, kNN이 청크 3을 찾았다면 두 기여를 문서 단위로 합산하지 않는다. 결합 키는 chunk_id다.

BM25와 벡터의 원시 점수 스케일이 달라 직접 합산하기 어렵다. 기존 min-max는 후보 최솟값·최댓값으로 점수를 0~1로 늘렸고, 현재는 RRF로 그 정규화 의존성을 줄였다. 다만 코퍼스가 바뀌어 원래 순위가 바뀌면 RRF 결과도 바뀐다. “데이터가 바뀌어도 순위가 안정적”이라는 보증은 아니다.

K가 커질수록 순위별 점수 차가 완만해진다. K=60에서 두 검색의 가중치는 동일하다. 제목 boost=2와 최신성 가산은 여전히 있으므로 시스템 전체에 가중치가 전혀 없는 것은 아니다.

## 6. 최신성 가산은 청크 후보에 적용한다

`_apply_recency_bonus()`는 updated_at이 있는 후보 **청크**를 최신순으로 정렬한다. 후보 수를 5구간으로 나누고 최대 가산점부터 0까지 차등 부여한다. 문서 중복 제거 전이므로 긴 문서의 여러 청크도 구간에 영향을 준다.

```text
최대 가산점 = RECENCY_BOOST_MAX × 2/(K+1)
기본값 = 0.04 × 2/61 ≈ 0.00131
```

현재 각 청크 점수의 4%를 곱하는 방식이 아니다. 후보가 5개 미만이면 생략한다. 수정 시각은 문서 내용의 사건 날짜가 아니고, 같은 날짜 후보의 경계 처리도 정답과 직접 관련된 것은 아니다.

## 7. 청크 후보를 원본 문서 5개로 줄이기

점수순으로 순회하며 `seen_doc_ids`에 있는 문서는 건너뛴다. 처음 발견된 최고 점수 청크를 해당 문서의 대표로 선택한다. 이 때문에 같은 문서 청크가 최종 다섯 자리를 독점하지 못한다.

다만 후보 50개를 얻는 단계에서는 이미 긴 문서 청크가 많은 자리를 차지할 수 있다. 후보에서 탈락한 다른 문서를 나중의 중복 제거가 되살리지는 못한다.

## 8. 문맥 재조립: 정확한 원상복구와는 다르다

선택된 doc_id들을 `terms` 쿼리 하나에 넣고 `doc_id`, `chunk_index` 순서로 정렬한다. 문서별로 한 번씩 조회하는 N+1 왕복을 줄인 구현이다. 본문 재조회에서는 doc_id와 text만 받으며, 후보 조회도 text_vector를 응답 필드에서 제외한다.

현재 `_group_chunk_texts()`의 핵심은 다음과 같다.

```text
누적 본문 길이가 3,000 이상이면 다음 청크는 건너뜀
아직 3,000 미만이면 현재 청크 전체를 추가
마지막에 개행으로 연결
```

따라서 2,800자에서 700자 청크를 추가하면 3,500자가 된다. 연결 개행과 프롬프트의 제목·경로는 별도다. 앞서 설명했던 “LLM 전체 본문 최대 15,000자”는 엄격한 상한으로는 잘못된 설명이다.

또한 다음 한계가 있다.

- overlap을 제거하지 않아 이웃 청크의 문장이 중복될 수 있다.
- 앞에서부터 연결하므로 길이 기준 뒤에 있는 정답 문단이 제외될 수 있다.
- 조회 size는 `선택 문서 수 × 50`이다. 5개 문서이면 전체 최대 250개 hit이며 문서당 50개 보장이 아니다.
- 문서가 결과에 없거나 본문이 비면 대표 청크로 대체한다. 재조회 자체가 예외를 던지면 해당 대체 로직까지 도달하지 않는다.

## 9. 검색 실패와 빈 결과

첫 BM25/kNN 요청 블록은 예외를 잡아 빈 배열을 반환한다. 따라서 일부 검색 장애가 상위에서 정상적인 “검색 결과 없음”처럼 처리될 수 있다. 재조립 요청은 그 try 블록 밖이다.

검색 결과 0건 자체도 모든 질문의 실패를 뜻하지 않는다. 문서에 없는 질문을 정직하게 거절하거나, 이력만으로 답할 수 있는 질문은 별도로 해석해야 한다.

## 10. 발표에서 설명할 핵심

“작은 청크로 후보를 찾고, 두 검색의 순위를 결합한 뒤, 서로 다른 원본 문서를 골라 문맥을 확장한다.” 여기까지가 실제 구현의 중심이다. 정답 확률이 높아졌다는 주장은 [평가 조건과 결과](04-evaluation.md)를 함께 설명해야 한다.
