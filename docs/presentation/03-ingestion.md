## 2. 전체 실행 순서

```text
1. 카테고리·본문 수집
2. 전체 실행이면 원본에서 삭제된 문서 정리
3. 수정 시각 비교로 재색인 대상 선정
4. 대상 본문 파싱·청킹
5. 인덱스 존재 확인 / 대상의 기존 청크 삭제
6. 제목+청크 본문 임베딩
7. 벡터와 청크 bulk 색인
```

파싱·청킹은 기존 청크를 지우기 전에 한다. 이전 발표 축 문서의 순서 그림은 이 순서를 거꾸로 표현했으므로 정정했다.

## 3. 증분 색인의 실제 범위

`get_indexed_updated_ats()`는 대상 doc_id들로 검색 범위를 제한하고 `size=0`으로 본문을 받지 않는다. `terms` 집계로 doc_id별 그룹을 만들고 `max(updated_at)`의 문자열 값을 얻는다. 주석에 collapse라고 적혀 있지만 실행 쿼리는 집계다.

```text
stored[page.id] == page.last_updated → 건너뜀
다르거나 없음 → 재색인
```

현재는 시각을 정규화해 비교하는 것이 아니라 문자열을 비교한다. 같은 순간이라도 문자열 형식이 달라지면 불필요한 재색인 대상이 될 수 있다. 파서나 임베딩 모델을 바꿨는데 원본 수정일이 같으면 자동 재색인되지 않으므로 강제 처리나 새 인덱스가 필요하다.

증분이라는 말은 본문 API 트래픽 전체를 절약한다는 뜻도 아니다. 일반 실행은 본문을 가져온 뒤 ES의 저장 시각과 비교한다. 수집 함수의 modified_since도 받아온 결과를 걸러내며, 현재 ingest는 이를 전달하지 않는다. 주로 절약되는 것은 이후 파싱·임베딩·색인 작업이다. 비용 절감률은 별도로 측정하지 않았다.

## 4. 고아 청크가 생기는 이유

청크 ID는 원본 ID와 순번으로 만든다. 문서가 5청크에서 3청크로 줄어든 경우를 보자.

| 단계 | ES에 남는 청크 |
|---|---|
| 수정 전 | 0, 1, 2, 3, 4 |
| 새 0~2만 upsert | 새 0, 새 1, 새 2, 옛 3, 옛 4 |
| 기존 전체 삭제 후 새 색인 | 새 0, 새 1, 새 2 |

옛 3, 4가 고아 청크다. 원본에서 사라진 규정이 검색·답변에 다시 등장할 수 있다. 현재 구현은 재색인 대상 **문서 ID 전체**를 먼저 지우기 때문에 새 본문이 비어 0청크가 된 문서도 처리한다. 새 청크에 나타난 ID만 삭제 대상으로 삼았다면 그 빈 문서는 빠졌을 것이다.

본문 없는 문서는 ES에 저장된 수정일도 없으므로 다음 실행에서도 재색인 후보가 될 수 있다. `empty_docs` 로그로 그 수를 드러낸다.

## 5. 원본 문서 삭제와 청크 축소는 다른 사건

문서 자체가 Confluence에서 삭제되면 수정된 본문이 수집되지 않는다. 따라서 고아 청크 정리와 별도로 집합 차이를 계산한다.

```text
stale_ids = indexed_ids - live_ids
삭제 대상 = ES에는 있지만 현재 Confluence 목록에는 없는 ID
```

Confluence 쪽은 ID 목록을 끝까지 페이지네이션한다. ES 쪽은 `composite` 집계를 1,000개씩 넘기며 `after_key`로 다음 페이지를 요청한다. 본문을 가져오지 않고 고유 문서 ID만 모은다.

여기서 ES ID 목록이 잘리면 삭제해야 할 문서를 놓칠 수 있고, Confluence ID 목록이 잘리면 정상 문서를 삭제 대상으로 오해할 수 있다. 두 오류의 방향이 다르다.

## 6. 삭제 안전장치와 실제 제한

| 조건 | 현재 처리 |
|---|---|
| `--limit` 또는 `--category` | 삭제 동기화 생략 |
| `--no-prune` | 삭제 동기화 생략 |
| 원본 전체 ID 조회 중 예외 | 예외를 올리고 해당 삭제 단계 생략 |
| 원본 전체 ID가 빈 목록 | 삭제 생략 |
| 전체 목록 차이가 없음 | 삭제 호출 없음 |

전체 수집이 성공해도 수집 계정의 가시성 변화와 실제 삭제를 구분하는 별도 로직은 없다. `delete_documents_by_ids()`는 실패 시 0을 반환하므로 “삭제할 것 없음”과 “삭제 실패”는 로그를 함께 봐야 구분된다.

## 7. 임베딩과 bulk 배치

임베딩 입력은 `title + '\n' + text`다. 기본 50개씩 LiteLLM에 요청해 vectors에 누적한다. ES bulk는 200개씩 처리한다. 검색 후보 수 50과 임베딩 배치 50은 우연히 숫자가 같을 뿐 서로 독립적이다.

`index_document_chunks()`는 chunk_id를 ES `_id`로 사용한다. 동일 ID에 다시 index하면 기존 문서가 대체된다. bulk는 `raise_on_error=False`로 부분 실패를 집계하고 성공 개수를 반환한다. 모든 청크가 반드시 성공할 때까지 자동 복구하는 작업 큐는 없다.

중요한 한계는 기존 청크를 지운 **뒤에** 임베딩을 한다는 것이다. 임베딩 API나 bulk가 실패하면 해당 문서가 비거나 일부만 남을 수 있다. 삭제와 재색인은 하나의 원자적 트랜잭션이 아니다. “고아 청크를 정리한다”와 “재색인이 무조건 무중단·무손실이다”를 구분해야 한다.

## 8. alias와 전체 인덱스 교체

기본 검색 대상은 `confluence-current`, 실제 인덱스 기본값은 `confluence-openai-v3`다. alias는 검색 대상에 붙인 이름표다.

```text
검색 코드 → confluence-current → 기존 인덱스
                           새 인덱스 준비·검증
검색 코드 → confluence-current → 새 인덱스
```

`create_confluence_index()`는 최초 인덱스 생성과 alias 연결을 한다. 이미 대상이 있으면 그대로 반환한다. 실행할 때마다 새 버전 생성·복사·검증·전환을 자동 수행하지는 않는다. 과거 전환 절차는 [RETRIEVAL.md](../RETRIEVAL.md)에 기록돼 있다.

분석기만 바꾸는 경우 기존 벡터를 복사할 수 있지만, 임베딩 모델을 바꾸면 같은 차원이어도 의미 공간이 달라질 수 있으므로 재임베딩이 필요하다. alias 교체와 일상 증분 색인의 삭제 후 재삽입은 서로 다른 운영 경로다.

## 9. 실행 옵션의 의미

| 옵션 | 의미 |
|---|---|
| 없음 | 전체 수집 후 변경분 색인 + 삭제 정리 |
| `--force` | 수정일이 같아도 다시 처리 |
| `--limit 10` | 수집 결과에서 일부만 처리. 현재 전체 본문 수집 자체를 10개로 제한하지 않음 |
| `--category` | level_1로 ID를 고른 뒤 해당 본문 조회 |
| `--batch-size` | 임베딩 요청당 입력 개수 |
| `--no-prune` | 원본 삭제 동기화만 생략. 재색인 대상의 옛 청크 삭제는 수행 |

이 축에서 설명할 판단은 “바뀌지 않은 데이터는 재처리하지 않고, 사라진 데이터는 검색 근거로 남기지 않는다”이다. 자동 스케줄러·Airflow·원자적 교체까지 구현했다고 확장하지 않는다.
