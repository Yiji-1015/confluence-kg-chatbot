## 2. 노트북 열기와 실행

저장된 출력부터 확인한다. VS Code나 Jupyter에서 노트북을 열고 CAP-01 등의 출력 영역을 캡처하면 된다. HTML 출력이 숨겨지면 코드를 검토한 뒤 신뢰한 노트북으로 열거나 직접 재실행한다. 뷰어의 HTML·CSS 지원에 따라 표와 나란히 배치한 패널의 모양이 달라질 수 있다.

다시 실행하려면 별도 Python 환경에서 저장소 루트 기준으로 다음 패키지를 설치하고, 해당 환경을 노트북 커널로 선택한다.

```bash
python -m pip install -r notebooks/requirements-presentation.txt
```

그 뒤 셀을 위에서 아래로 모두 실행한다. 실행 위치는 저장소 루트 또는 그 아래 `notebooks/`여야 한다. Python 3.9 이상을 사용하며 검증에 사용한 직접 의존성 버전은 requirements 파일에 고정했다. 이는 서비스 전체의 의존성 잠금 파일은 아니다.

이 노트북은 외부 API·LLM·ES 검색을 호출하지 않는다. `.env`가 없어도 기본 설정으로 import할 수 있다. `.env`가 있는 환경에서는 프로젝트 설정 모듈이 읽을 수 있지만 인증정보나 설정 전체를 출력하지 않는다. 함수 기본값 변화가 예시를 조용히 바꾸지 않도록 청킹 800/150, RRF K=60, 재조립 3,000자, 검색 이력 1회를 명시했다.

## 3. 무엇을 캡처할까

| ID | 캡처 범위 | 슬라이드에서 짚을 부분 |
|---|---|---|
| CAP-01 | 원본 표와 Markdown 출력 전체 | 운영팀의 세로 병합과 공통 안내의 가로 병합이 펼쳐짐 |
| CAP-02 | 청크 메타데이터와 노란색 공통 부분 | 문서 ID·청크 순서, 실제 경계에서의 overlap |
| CAP-03 | 검색됐다고 가정한 청크와 재조립 출력 | 설치 안내뿐 아니라 기능 설명도 문맥에 포함 |
| CAP-04 | RRF 점수 표 전체 | 한 목록의 1위보다 양쪽에 등장한 청크가 앞서는 예시 |
| CAP-05 | 직전 질문·현재 질문·검색 문자열 | LLM 재작성 없이 문자열로 이전 주제어를 추가 |

본문에는 CAP-01~03을 우선 사용한다. CAP-04~05는 보조 장표나 질문 대비용이다. 실행 코드 전체를 캡처하지 말고 **출력의 제목·시연 데이터 표기·본문·설명**이 함께 들어오도록 캡처한다. CAP-02는 출력만 경계 부분을 발췌했고 실제 청킹은 전체 가상 문서에 수행했다.

가상 입력은 회사 데이터 노출 없이 동작을 설명하기 위한 것이다. 합성 예시를 실서비스 검색 결과나 성능 개선 실험으로 소개하지 않는다. 재조립 출력의 반복 문장을 지워 ‘완전한 원문 복원’처럼 보이게 편집하지 않는다.

## 4. Langfuse에서 준비할 평가 캡처

실제 화면은 사용자가 접근 가능한 프로젝트에서 촬영한다. 이 문서는 특정 버전의 메뉴 위치를 전제로 하지 않고, 담겨야 할 정보를 지정한다. 없는 실행·점수 화면을 새로 그려 실제 캡처처럼 사용하지 않는다.

### LF-01: 평가 실행과 점수

한 화면 또는 인접한 두 화면에서 다음을 식별할 수 있게 한다.

- 데이터셋·실행을 구별할 수 있는 이름과 실행 시점
- 지표 이름과 평균 점수
- 가능하면 지표별 채점 건수 또는 대상 문항 수

원고에 인용한 기록은 2026-09-14 KST 기준이다. UTC로 표시된 09-13 실행과 날짜 표기가 다를 수 있으므로 실행 이름과 값을 함께 대조한다.

| 구분 | 지표 | 기록값 | 채점 범위 |
|---|---|---:|---:|
| 검색 | hit@5 | 0.974 | 38문항 |
| 검색 | MRR | 0.908 | 38문항 |
| 생성 | 자체 correctness | 0.958 | 45문항 |
| 생성 | 자체 faithfulness | 0.973 | 45문항 |
| 생성 | RAGAS faithfulness | 0.856 | 45문항 |
| 생성 | RAGAS context precision | 0.851 | 45문항 |

근거: [CHANGELOG.md](../CHANGELOG.md)의 Langfuse 원본 대조 기록, [평가 상세](04-evaluation.md). 실제 캡처 값이 다르면 위 숫자에 맞추려고 화면을 편집하지 않는다. 다른 실행인지 확인하고, 다른 실행의 점수는 별도 조건으로 소개한다.

**중요:** 슬라이드의 BM25/kNN/RRF 비교는 [EVALUATION.md](../EVALUATION.md)의 검색 비교 실험 기록이다. Langfuse에 그 비교 실행이 없다면 LF-01은 평가 관리 사례로만 사용하고, 세 방식의 비교 근거는 기록 기반 표로 제시한다. 검색 비교를 재현하기 위해 새 API 평가를 돌릴 필요는 없다.

### LF-02: 문항 하나를 열어본 사례

질문, 생성 답변, 기대 답변 또는 검색 근거, 개별 평가 점수를 함께 읽을 수 있는 사례를 고른다. 성공 사례도 가능하고 낮은 점수를 다시 검토하는 사례도 가능하다. 문항 하나가 전체 품질을 대표한다고 설명하지 않는다.

요청 trace의 검색·생성 소요 시간은 실행 과정의 근거다. 지연 화면만으로 답변 정확도나 검색 품질을 입증한다고 말하지 않는다. trace 캡처를 추가한다면 6장의 관측 설명이나 보조 자료에 둔다.

### 외부 발표 전 가릴 정보

회사·고객·직원 실명, 비공개 문서 제목·본문, 내부 URL, 이메일, 프로젝트 식별정보, 인증정보가 보이지 않는지 확인한다. 내용 공개 권한이 불분명하면 해당 사례 대신 점수 요약 화면을 사용한다. 마스킹 후에도 지표 이름·측정 조건·점수는 읽을 수 있어야 한다.
