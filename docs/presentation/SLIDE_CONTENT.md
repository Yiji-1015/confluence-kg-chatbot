# EY 데이터분석 인턴 면접 — 10분 발표 콘텐츠 원고

## Claude에 전달할 제작 요청

이 파일을 바탕으로 한국어 프로젝트 발표 자료를 만든다. 본문은 7장, 발표 배정 시간은 총 10분이다. 이 파일은 내용 명세이며 색상·폰트·레이아웃은 지정하지 않는다.

- 각 장의 **화면 문구**만 슬라이드 본문으로 사용한다. **발표자 노트**, **근거**, **제작 유의사항**을 본문에 그대로 붙이지 않는다.
- 캡처는 아래 자산 ID로 연결한다. 아직 전달되지 않은 이미지는 해당 ID의 이미지 자리만 남기고, 실제 서비스 화면이나 결과를 만들어내지 않는다.
- 기록된 수치와 시연 데이터를 섞지 않는다. 모든 캡처의 구분 문구·수치의 측정 조건은 유지한다.
- 프로젝트에 구현된 기능과 발표자가 직접 작성한 코드는 구분한다. 직접 기여가 확인된 파싱 외에 개인 구현 범위를 추정하지 않는다.
- 실제 사용자 조사, 검색 시간 단축, 비용 절감률, 운영 트래픽, 통계적 유의성을 추가하지 않는다.
- 날짜가 포함된 제목을 여러 표현으로 확장해 색인하는 기능은 현재 구현이 아니다. `title_search`와 날짜 확장 함수는 제거됐고, 질문 날짜 정규화도 실험 후 미채택됐다. 이를 현재 기능으로 소개하지 않는다. 현재 검색어 보정은 직전 사용자 발화를 현재 질문 앞에 붙이는 방식이다.
- 지원 직무는 사용자가 제공한 EY 컨설팅부문 데이터분석 인턴 공고다. 데이터 처리, 분석·인사이트 도출, AI 프로젝트 경험과 연결하되 시장 조사나 거버넌스 전략을 수행한 프로젝트로 바꾸지 않는다.
- 본문 7장 뒤의 보조 자료는 발표 시간에 포함하지 않는다. 본문에 기능을 추가해 분량을 늘리지 않는다.

발표 전체 메시지: **비정형 문서를 검색 가능한 데이터로 만들고, 평가 질문의 조건까지 검토해 검색 설계의 타당성을 확인했다.**

## 장표 구성과 시간

| 장 | 제목 | 시간 | 누적 | 주요 자산 |
|---|---|---:|---:|---|
| 1 | 사내 문서에서 답변의 근거를 찾는 RAG | 0:45 | 0:45 | 없음 |
| 2 | 문서가 답변이 되기까지 | 0:45 | 1:30 | 흐름도 내용 제공 |
| 3 | 병합 표의 관계를 검색 가능한 텍스트로 | 2:00 | 3:30 | CAP-01, CAP-02 |
| 4 | 청크를 찾고, 문서 단위로 문맥을 모으다 | 2:00 | 5:30 | CAP-03 |
| 5 | 높은 점수보다 평가 질문의 조건을 확인하다 | 2:00 | 7:30 | LF-01, 비교 표 |
| 6 | 변경되는 문서와 이어지는 대화를 처리하다 | 1:30 | 9:00 | 세 가지 대응 표 |
| 7 | 데이터 가공에서 근거 있는 판단까지 | 1:00 | 10:00 | 없음 |

시간은 캡처를 짚어 설명하고 장표를 전환하는 시간을 포함한 배정이다. 원고를 빠르게 읽어서 10분을 채우는 방식이 아니라, 리허설에서 설명 속도를 맞춘다.

## 1. 사내 문서에서 답변의 근거를 찾는 RAG

### 화면 문구

제목: **사내 문서에서 답변의 근거를 찾는 RAG**

부제: Confluence 문서 정제 · 하이브리드 검색 · 평가

- 목표: 자연어 질문에 관련 문서를 찾아 답변과 원문 출처 제공
- 데이터 과제: HTML·병합 표·계층 정보가 섞인 비정형 문서
- 검증 과제: 질문의 표현이 달라져도 관련 문서를 찾는가?

작은 설명: 발표 초점 — 데이터 정제 / 검색 설계 / 평가에서 얻은 인사이트

### 발표자 노트 — 45초

이 프로젝트는 Confluence 문서를 검색하고, 찾은 문서를 근거로 답변과 원문 출처를 제공하는 RAG 서비스입니다. 단순히 언어 모델을 연결하는 것보다 두 가지를 중요하게 봤습니다. 첫째는 표와 계층 정보가 섞인 문서를 검색 가능한 형태로 바꾸는 것이고, 둘째는 검색 점수가 실제로 어떤 질문 조건에서 유효한지 확인하는 것입니다. 오늘은 전체 기능을 나열하기보다 데이터 정제, 검색 방식, 평가에서 발견한 점을 중심으로 설명하겠습니다. 특히 파싱은 제가 직접 작성한 로직을 구체적인 입력과 출력으로 보여드리겠습니다.

### 근거·제작 유의사항

- 프로젝트 목적은 [발표 축 요약](../PRESENTATION_AXES.md), 처리 코드는 [chat.py](../../ai-server/app/api/v1/chat.py).
- 인터뷰·사용자 설문·도입 전후 시간 측정이 있었다는 문장을 추가하지 않는다.
- 이름·학교·전공·개발 기간·팀 규모는 이 파일에 제공되지 않았으므로 임의로 넣지 않는다.

## 2. 문서가 답변이 되기까지

### 화면 문구

제목: **문서가 답변이 되기까지**

흐름도에 사용할 정확한 구성. 괄호 안 기술명은 해당 단계에 함께 표시한다:

```text
데이터 준비
Confluence REST API → HTML·표 정제(Python·BeautifulSoup)
 → 청킹(LangChain Text Splitters)·메타데이터 → 임베딩·Elasticsearch

질문 처리
사용자 질문 → Spring Boot(Java) → FastAPI(Python)
 → 질문 임베딩 + Elasticsearch 검색(Nori BM25·Vector kNN)
 → RRF·문서 선택 → 문맥 재조립 → LiteLLM → 답변·원문 출처

대화 저장: PostgreSQL(전체 기록) / Redis(최근 이력 캐시)
```

흐름도 아래 기술스택 한 줄: **평가·관측: RAGAS · Langfuse · Prometheus · Grafana | 실행 환경: Docker Compose**

모델 표기(작은 보조 문구): 임베딩 `text-embedding-3-small` / 답변 생성 DeepSeek·GPT-4o — LiteLLM 경유

하단 문구: **정제는 검색할 데이터를 만들고, 검색은 답변의 근거를 고른다.**

### 발표자 노트 — 45초

전체 흐름은 데이터 준비와 질문 처리로 나뉩니다. Python과 BeautifulSoup으로 문서를 정제하고, 청킹한 내용을 임베딩과 함께 Elasticsearch에 저장합니다. Spring Boot는 채팅과 세션 처리를, FastAPI는 검색과 AI 처리를 담당합니다. 검색 결과를 문맥으로 모아 LiteLLM으로 답변을 생성하고 출처를 반환합니다. 전체 대화는 PostgreSQL에, 최근 이력은 Redis에 저장합니다. 하단은 품질 평가와 실행 과정을 관찰하는 도구들입니다. 이제 그중 검색의 입력을 만드는 파싱 과정을 구체적으로 설명하겠습니다.

### 근거

[ingest.py](../../ai-server/scripts/ingest.py), [es_client.py](../../ai-server/app/retrieval/es_client.py), [chat.py](../../ai-server/app/api/v1/chat.py).

기술스택은 프로젝트 전체 구성이지 개인 기여 목록이 아니다. LangChain은 Text Splitters 사용으로 한정해 표기하며, 전체 RAG를 LangChain으로 구성했다고 쓰지 않는다. 도식의 Spring Boot와 FastAPI는 요청 처리 경계이며 모델 라우팅은 답변 생성 전에 수행된다. 스택만을 위한 별도 장표는 추가하지 않아 7장·10분 구성을 유지한다.

## 3. 병합 표의 관계를 검색 가능한 텍스트로

### 화면 문구

제목: **병합 표의 관계를 검색 가능한 텍스트로**

핵심 문장: **태그를 지우는 데서 끝내지 않고, 행·열 관계를 텍스트에 남겼다.**

CAP-01 옆 설명:

1. `rowspan`: 같은 값이 적용되는 다음 행에 값을 채움
2. `colspan`: 병합된 열의 자리를 펼침
3. 행별 레코드를 Markdown 표로 변환

CAP-02 옆 설명:

- 약 800자 기준 분할, overlap 설정 150자
- `doc_id`: 어떤 문서인가 / `chunk_index`: 몇 번째 조각인가
- overlap은 분할 경계에 따라 달라지며 항상 150자는 아님

### 캡처

- **CAP-01**: 노트북의 원본 병합 표와 파싱 결과. 주 이미지로 사용한다.
- **CAP-02**: 인접 청크 두 개와 실제 공통 부분 강조. 보조 이미지로 사용한다.
- 캡처의 ‘시연용 가상 문서 · 실제 프로젝트 함수 실행’ 표기를 유지한다.
- 공간이 부족하면 CAP-02 전체 대신 청크 요약 표만 사용한다. 글자를 작게 줄여 두 캡처 전체를 억지로 넣지 않는다.

### 발표자 노트 — 2분

제가 직접 작성한 부분 중 하나는 Confluence 문서를 검색용 텍스트로 바꾸는 파서입니다. 이 표는 동작을 설명하기 위한 가상 문서이고, 출력은 실제 프로젝트 파서를 실행한 결과입니다. 왼쪽에서 운영팀은 두 행에 걸쳐 있고, 공통 안내는 두 열에 걸쳐 있습니다. 태그를 제거해 글자만 나열하면 어떤 담당자와 안내가 같은 행에 속하는지 읽기 어려워질 수 있습니다.

그래서 표를 바로 문자열로 바꾸지 않고, 먼저 행과 열의 그리드로 펼쳤습니다. 세로 병합은 남은 행 수와 값을 기억해 다음 행에 채우고, 가로 병합은 차지하는 열 수만큼 같은 값을 채웁니다. 이후 첫 헤더를 기준으로 각 행을 레코드로 만들고 Markdown 표로 변환합니다. 오른쪽에서는 병합된 팀명이 각 행에 반복되고, 열 위치가 유지되는 것을 볼 수 있습니다.

다음은 이 텍스트를 검색 단위로 나누는 과정입니다. 설정은 약 800자와 overlap 150자이고, 문단·줄바꿈·공백 순으로 경계를 찾습니다. 이때 overlap은 무조건 150자를 복사하는 뜻은 아닙니다. 화면에서는 실제 인접 청크에 남은 공통 문자열을 표시했습니다. 각 조각에는 문서 ID와 청크 순서를 붙여, 검색 후 다시 같은 문서의 문맥을 모을 수 있게 합니다.

이 시연은 구조가 어떻게 변하는지를 보여주는 것이며, 파싱만으로 정확도가 몇 퍼센트 올랐다는 비교 실험을 의미하지는 않습니다.

### 근거

[confluence_parser.py](../../ai-server/app/parser/confluence_parser.py): `parse_confluence_html`, `_table_to_records`, `_table_records_to_markdown`, `split_text_into_chunks`.

## 4. 청크를 찾고, 문서 단위로 문맥을 모으다

### 화면 문구

제목: **청크를 찾고, 문서 단위로 문맥을 모으다**

```text
BM25: 단어 일치 후보 청크 50개 ─┐
                              ├→ RRF 순위 결합 → 서로 다른 문서 최대 5개
kNN: 의미 유사 후보 청크 50개 ─┘                  ↓
                                      문맥 재조립 → LLM
```

- 서로 다른 점수 척도 대신 각 검색의 순위를 결합
- 같은 문서의 여러 청크가 최종 문서 수를 차지하지 않도록 선택
- 선택 문서의 청크를 순서대로 이어붙여 주변 문맥 전달

이미지 설명: **검색된 한 조각 → 같은 문서의 문맥을 모은 결과**

작은 주석: 문서당 3,000자를 청크 추가 중단 기준으로 사용. 엄격한 글자 수 상한이나 원문 전체 복원은 아님.

### 캡처

**CAP-03**을 사용한다. 실제 ES 검색 결과가 아니라 정렬된 시연 청크를 프로젝트 재조립 함수에 넣은 결과다. 후보 50개→문서 최대 5개는 위 도식으로 설명하며, 작은 시연 데이터가 실제 후보 검색을 재현한 것처럼 표시하지 않는다.

### 발표자 노트 — 2분

검색에서는 질문에 문서의 단어가 직접 등장하는 경우와, 같은 뜻을 다른 표현으로 묻는 경우를 함께 고려했습니다. BM25는 단어 일치를 보고, kNN은 임베딩의 의미적 유사성을 봅니다. 각각 후보 청크를 50개씩 가져오지만, 이 50개를 모두 언어 모델에 넣는 구조는 아닙니다.

두 결과는 RRF로 결합합니다. BM25와 벡터 검색의 원래 점수는 척도가 달라서, 여기서는 각 목록의 순위로 점수를 계산합니다. 양쪽 목록에 함께 등장한 청크는 두 기여를 받습니다. 결합과 최신성 가산 이후 같은 문서의 중복을 제거해, 최종적으로 서로 다른 문서를 최대 다섯 개 고릅니다.

그다음 중요한 과정이 문맥 재조립입니다. 화면 왼쪽의 설치 안내 청크가 검색됐다고 해도, 같은 문서의 다른 청크에 기능 설명이 있을 수 있습니다. 선택된 문서의 청크를 순서대로 다시 모으면 오른쪽처럼 주변 내용도 전달할 수 있습니다. 다만 원본 HTML을 복원하는 것은 아니고, 청크를 이어붙이는 방식이라 overlap 중복은 남습니다. 길이 제한 때문에 전체 문서가 항상 들어가는 것도 아닙니다.

정리하면 앞 단계에서는 청크로 잘게 나눠 관련 부분을 찾고, 뒤 단계에서는 문서 단위로 근거를 모읍니다. 이런 설계가 실제로 도움이 되는지는 검색 방식별 평가로 확인했습니다.

### 근거

[es_client.py](../../ai-server/app/retrieval/es_client.py): `_rrf_scores`, `search_hybrid`, `_fetch_full_doc_texts`, `_group_chunk_texts`.

## 5. 높은 점수보다 평가 질문의 조건을 확인하다

### 화면 문구

제목: **높은 점수보다 평가 질문의 조건을 확인하다**

발견: **원본 질문에 문서 제목의 단어가 많이 포함되어 있었다.**

대응: 같은 정답 문서를 유지하도록 질문을 바꾼 paraphrase 대조군으로 비교

| 검색 방식 | 원본 질문 MRR | Paraphrase 질문 MRR |
|---|---:|---:|
| BM25 | 0.864 | 0.390 |
| kNN | 0.812 | 0.501 |
| RRF | 0.908 | 0.560 |

결론: **이 대조군에서는 RRF가 BM25보다 MRR 0.170 높았다.**

각주: 2026-09-14 기록 / 583문서·3,211청크 / 검색 38문항 / MRR은 정답 문서의 첫 등장 순위 역수의 평균.

한계: 합성 질문·작은 표본. 모든 사용자 질문에 대한 개선으로 일반화하지 않음.

### 캡처

- **LF-01**: 실제 Langfuse 평가 실행의 점수·채점 건수 확인 화면. 비교 표의 보조 근거로 사용한다.
- BM25/kNN/RRF 비교 표의 출처는 저장소의 검색 비교 기록이다. Langfuse에 세 방식의 실행이 실제로 없으면, 캡처가 이 비교를 직접 보여준다고 설명하지 않는다.
- 점수 표와 캡처가 좁으면 표를 본문에 남기고 LF-01은 보조 장표로 옮긴다. trace 화면으로 평가 결과를 대체하지 않는다.

### 발표자 노트 — 2분

검색은 정답 문서를 상위 다섯 개 안에 찾는지와, 얼마나 앞에 찾는지를 나눠 봤습니다. 여기서는 순위를 보는 MRR을 중심으로 설명하겠습니다. 정답이 첫 번째면 1점, 두 번째면 0.5점이고, 못 찾으면 0점입니다.

원본 질문에서는 RRF의 MRR이 0.908이었습니다. 그런데 점수만 보기보다 평가 질문의 구성을 살펴볼 필요가 있었습니다. 데이터셋 생성 프롬프트가 문서를 특정할 수 있는 단서를 넣도록 되어 있어, 제목의 단어가 질문에 많이 등장했습니다. 이런 조건은 키워드 검색에 유리할 수 있습니다.

그래서 같은 정답 문서를 겨냥하되 제목 표현을 줄이고 동의어나 구어체를 쓰도록 질문을 바꿔 비교했습니다. 표를 보면 BM25는 0.864에서 0.390으로, RRF는 0.908에서 0.560으로 내려갑니다. 질문 조건이 바뀌면 평가 점수도 크게 달라집니다. 동시에 이 대조군에서는 RRF가 BM25보다 0.170 높아, 의미 검색을 함께 쓰는 실익이 관찰됐습니다.

다만 이것을 모든 질문에서 성능이 보장된다고 해석하지는 않았습니다. 검색 표본은 38문항이고 질문도 합성 데이터입니다. 질문을 바꿨다고 모든 편향이 제거된 것도 아닙니다. 이 경험에서 강조하고 싶은 점은 높은 점수 하나보다, 어떤 조건에서 얻은 결과인지 확인하고 비교 조건을 바꿔 판단하는 과정입니다.

## 6. 변경되는 문서와 이어지는 대화를 처리하다

### 화면 문구

제목: **변경되는 문서와 이어지는 대화를 처리하다**

| 서비스에서 마주치는 상황 | 프로젝트의 처리 방식 |
|---|---|
| 문서가 바뀌거나 사라짐 | 수정 시각 기반 재처리 판단, 기존 청크·삭제 문서 정리 |
| 사용자가 후속 질문을 함 | 직전 사용자 발화를 검색어에 추가, 대화 이력을 생성에 전달 |
| 모델 호출과 지연을 확인해야 함 | LiteLLM 라우팅, Langfuse 요청 추적, Grafana 집계 |

검색을 실제 대화 흐름으로 연결하면서는 세 가지 상황을 함께 다뤘습니다. 첫 번째는 문서 변경입니다. 매번 모든 문서를 다시 임베딩하는 대신 수정 시각을 비교해 변경되지 않은 문서는 처리를 생략합니다. 수정으로 문서가 짧아졌을 때는 기존 청크를 정리하고 다시 색인하며, 원본에서 삭제된 문서도 별도로 반영합니다. 비용 절감률을 측정한 것은 아니지만 불필요한 임베딩 호출을 줄이는 구조입니다.

두 번째는 후속 질문입니다. 사용자가 '그건 언제까지야?'라고 물으면 그 문장만으로 주제를 찾기 어렵습니다. 현재는 직전 사용자 발화를 검색어 앞에 붙이고, 답변 생성에는 대화 이력을 전달합니다. 전체 기록은 PostgreSQL에, 최근 다섯 턴은 Redis에 보관합니다. 이 기능은 현재의 단일 질문 평가와는 구분합니다.

세 번째는 모델 호출과 관찰입니다. LiteLLM을 통해 모델을 호출하고, 질문과 이력 길이에 따른 규칙으로 모델을 선택합니다. Langfuse는 요청별 과정을, Grafana는 여러 요청의 지연과 단계별 소요 시간을 보는 역할입니다. 이 부분은 검색·평가를 사용 흐름에 연결한 구성으로 설명하겠습니다.

## 보조 자료 내용 — 10분 본문에 포함하지 않음

### A. RRF의 계산

- CAP-04 사용. `점수 = Σ 1 / (60 + 해당 검색에서의 순위)`.
- 해당 후보 목록에 없는 청크는 그 목록의 기여가 0이다.
- 시연은 RRF만 분리해 보여준다. 실제 검색에는 이후 최신성 가산과 문서 중복 제거가 있다.
- RRF는 정답 확률이 아니다. 합성 후보의 순위 변경은 실서비스 성능 개선 증거가 아니다.

### B. 멀티턴이 검색에 들어가는 방식

- CAP-05 사용. `직전 사용자 발화 + 현재 질문`.
- LLM이 질문을 독립 문장으로 재작성하는 구현이 아니다.
- 주제가 바뀌면 이전 발화가 불필요한 단서가 될 수 있다. 멀티턴 정량 평가를 수행했다는 의미가 아니다.

### C. 생성 품질 평가와 실제 사례

- LF-01 또는 LF-02 사용.
- 2026-09-14 기록: 자체 correctness 0.958, 자체 faithfulness 0.973, RAGAS faithfulness 0.856, RAGAS context precision 0.851. 각각 채점 45문항.
- 검색 hit@5 0.974, MRR 0.908은 검색 대상 38문항. 생성 45문항과 분모가 다르다.
- 서로 다른 지표를 하나의 ‘정확도’로 합치지 않는다. 실제 캡처가 다른 실행이면 그 실행의 값과 조건으로 별도 표시한다.
