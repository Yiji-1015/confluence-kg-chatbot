# 슬라이드 1 · 무엇을 재는가

## 한 줄 메시지

> **"답이 틀렸다"로는 고칠 수 없다. "어디서 틀렸다"를 알아야 고친다.**

## 문제 상황

RAG 챗봇이 틀린 답을 했다. **어디를 고쳐야 하는가?**

```
질문 → [검색] → [컨텍스트 조립] → [LLM 생성] → 답변
         ↑            ↑               ↑
      검색을        프롬프트를        모델을
      고쳐야?        고쳐야?          바꿔야?
```

셋 다 손대보는 것은 비용이 크고, 무엇이 효과가 있었는지도 알 수 없다.
**단계별로 따로 재야 한다.**

## 지표 6개, 세 층위

| 층위 | 지표 | 무엇을 보는가 | 정답 라벨 |
|---|---|---|---|
| **검색** | `retrieval_hit@5` | 정답 문서가 상위 5건에 들었는가 (0/1) | 필요 |
| | `retrieval_mrr` | 정답 문서가 **몇 위**였는가 ($1/\text{순위}$) | 필요 |
| **생성 (자체 구현)** | `answer_faithfulness` | 답변이 **검색된 컨텍스트에만** 근거하는가 | 불필요 |
| | `answer_correctness` | 답변이 **기대 답변**과 맞는가 | 필요 |
| **생성 (표준·RAGAS)** | `ragas_faithfulness` | 위와 같은 것을 **표준 구현**으로 | 불필요 |
| | `ragas_context_precision` | 가져온 문서들이 **실제로 답변에 쓰였는가** | 불필요 |

## 왜 `hit@5`만으로는 부족한가

**`MRR`을 추가한 이유** — `hit@5`는 정답이 1위든 5위든 똑같이 1점이다.
결합 방식을 바꿔가며 재보면 `hit@5`는 전혀 안 움직이는데 MRR만 갈리는 경우가 많았다.

| 필드 결합 방식 | hit@5 | MRR |
|---|---|---|
| `best_fields` (현재) | 0.974 | **0.908** |
| `tie_breaker=0.3` | 0.974 | **0.908** |
| `most_fields` | 0.974 | **0.890** |

컨텍스트는 점수 순으로 이어 붙으므로 앞 순위일수록 답변에 강하게 작용한다.

**`ragas_context_precision`을 추가한 이유** — `hit`과 `MRR`은 **정답으로 라벨링한 문서 1개**만 본다.
함께 딸려온 나머지 4건의 품질은 전혀 보지 못한다.

> 실측(2026-09-01): 결합 방식을 바꾸자 상위 5개 구성이 **38건 중 33건에서 달라졌는데도
> `hit`은 완전히 동일**했다. 이 지표가 그 사각지대를 메운다.

## 측정 결과

**검색 지표** (2026-09-14 / 583문서 · 3,211청크 / 채점 38문항)

| 지표 | 값 |
|---|---|
| `retrieval_hit@5` | **0.974** |
| `retrieval_mrr` | **0.908** |

**생성 지표** (2026-09-08 / 45문항 / 판정 모델 `solar`)

| 지표 | 값 |
|---|---|
| `answer_correctness` | **0.970** |
| `ragas_context_precision` | 0.753 |

> 생성 지표는 검색 엔진 변경(09-13·09-14) 이전 측정값이다. 재측정하려면 판정 모델 호출이
> 필요해 보류했다. **측정 조건이 다른 값을 한 줄에 섞지 않는다.**

# 슬라이드 2 · 오답의 원인을 자동으로 가른다

## 한 줄 메시지

> **지표를 조합하면 "어느 단계가 고장났는지"가 나온다.**

## 판정 규칙

```
retrieval_hit = 0
    └→ 검색 실패        : 애초에 정답 문서를 못 찾았다
                          → 검색을 고친다 (가중치, 후보 수, 분석기)

retrieval_hit = 1
  faithfulness < 0.6
    └→ 컨텍스트 무시    : 문서는 찾았는데 LLM이 근거 없이 답했다
                          → 프롬프트를 고친다

retrieval_hit = 1
  faithfulness ≥ 0.6
  correctness 낮음
    └→ 이해·추론 실패   : 근거도 맞고 충실한데 결론이 틀렸다
                          → 모델을 바꾼다
```

## 실행하면 이렇게 나온다

```
=== 실패 원인 진단 ===
- [qa-v2-021] hit=0.0 faithfulness=0.95 correctness=0.2
    -> 검색 실패 (정답 문서를 못 찾음)
```

정답 처리된 문항(`correctness ≥ 0.7`)은 건너뛰고 **틀린 것만** 원인과 함께 출력한다.

## 이게 왜 중요한가

| | |
|---|---|
| 없을 때 | "정확도 93%" → **무엇을 고쳐야 할지 알 수 없다** |
| 있을 때 | "틀린 3건 중 2건은 검색 실패, 1건은 추론 실패" → **검색부터 손댄다** |

> 실제 적용 사례: 실패 3건을 열어보니 **2건은 지표 적용 오류**(본문 없는 문서를 검색
> 지표로 채점), **1건은 데이터셋 라벨 오류**(실제로 존재하는 문서를 out-of-domain으로 표기)였다.
> 모델 문제가 아니라 **측정 문제**였다.

## 채점 대상에서 빼는 문항

모든 문항을 같은 잣대로 채점하면 지표가 왜곡된다.

| 문항 유형 | 검색 지표 채점 | 이유 |
|---|---|---|
| Factoid (37건) | ✅ 채점 | 정답 문서가 명확하다 |
| **Known-gap** (2건) | ❌ 제외 | 겨냥한 문서가 본문이 없어 **색인에 존재하지 않는다.** 검색이 못 찾는 것이 정상이라, 채점하면 구조적으로 0점이 되어 지표를 깎는다 |
| **Out-of-domain** (6건) | ❌ 제외 | 사내 문서에 답이 **없는** 질문이다. 정답 문서 자체가 없다 |

제외한 문항은 `answer_correctness`로 **"모른다고 정직하게 답하는가"**, **"링크 안내로
답하는가"**를 본다. 45문항 중 **38문항**이 검색 지표 채점 대상이다.

# 슬라이드 3 · 측정 도구를 어떻게 믿는가

## 한 줄 메시지

> **측정값을 믿기 전에 측정 도구를 먼저 의심했다.**

이 직무와 가장 가까운 부분이다. AI 도입 컨설팅에서 "그 성능 수치, 어떻게 측정하셨죠?"를
물어야 하는 이유가 여기 다 있다.

## ① 채점자와 피채점자를 분리했다

| 역할 | 모델 |
|---|---|
| 답변을 생성하는 모델 | `deepseek-chat` 또는 `gpt-4o` (질문 길이에 따라 라우팅) |
| **점수를 매기는 판정 모델** | **`solar`** — 답변에 쓰이지 않는 제3의 모델 |

같은 모델이 답하고 채점하면 **자기 답변을 후하게 본다.**
판정 모델은 답변 생성에 쓰이는 두 모델 어느 쪽도 아닌 것으로 골랐다.

> 답변 모델 라우팅: 12자 미만의 짧은 질문과 총 1,000자 이상의 긴 맥락은 `gpt-4o`로,
> 나머지는 `deepseek-chat`으로 보낸다. 단서가 적을수록 의도 파악에 실패하는 사례가
> 실사용에서 관찰됐기 때문이다.

## ② 자체 지표를 표준 지표와 나란히 놓았다

직접 구현한 `answer_faithfulness` 옆에 **RAGAS 표준 지표**를 같이 기록한다.
**두 지표는 같은 판정 모델(`solar`)을 쓴다.** 모델이 다르면 공정한 비교가 안 되기 때문이다.

**그래서 드러난 것 (2026-09-01 기준선)**

| 지표 | 값 |
|---|---|
| `answer_faithfulness` (자체 구현) | **0.951** |
| `ragas_faithfulness` (표준) | **0.838** |
| **차이** | **0.113** |

**자체 지표가 0.113 후하게 채점하고 있었다.**

원인까지 확인했다. RAGAS는 답변을 **문장 단위로 쪼개 각 문장이 컨텍스트에 근거하는지
따로** 판정하는데, 자체 구현은 **답변 전체를 한 번에** 본다. 일부 문장이 근거 없어도
전체적으로 "근거함"으로 넘어간다.

> **자체 지표만 봤다면 실제보다 좋게 평가하고 있었다.**

## ③ 조용히 빠진 문항을 잡아낸다

**실제로 있었던 일 (2026-09-02).**
판정 모델 호출에서 429(요청 한도 초과)가 5건 발생했다. 재시도가 없어 그 문항들은
점수 없이 빠졌고, **45문항이 아니라 40문항 평균이 출력됐다.**

> 실행은 정상 종료되고 점수도 그럴듯해서 **로그를 보지 않으면 알 수 없었다.**

두 겹으로 막았다.

| 방어 | 무엇을 잡나 |
|---|---|
| 실패 사유별 집계 | **우리가 아는** 실패 (호출 실패, 파싱 실패) |
| 채점된 문항 수 ↔ 데이터셋 문항 수 대조 | **예상 못 한 경로**로 빠진 문항 |

그리고 출력이 침묵하지 않게 했다.

```
경고: 채점 실패 5건. 해당 문항은 평균 계산에서 빠졌으므로
      이 실행의 점수를 다른 실행과 비교하면 안 됩니다.
  - answer_correctness: 호출 실패(RateLimitError): 5건
```

누락이 없으면 **"채점 누락 없음"**을 찍는다. 침묵을 정상으로 오해하지 않게 하기 위해서다.

재발 방지는 게이트웨이에서 처리했다. 호출부마다 재시도를 넣지 않고 LiteLLM 한 곳에
`num_retries: 3`을 뒀다.

## ④ 어떤 설정으로 잰 값인지 이름에 남긴다

Langfuse 실행 이름을 설정값으로 만든다.

```
qa-bm25_4-knn_6-top5-cand50-chars3000-recency0.04-temp0-judge_solar-0914-1530
```

이름이 고정이면 목록에서 **어떤 설정의 실행인지 구분할 수 없어 기억에 의존하게 된다.**
끝의 시각은 같은 설정을 여러 번 돌려 재현성을 볼 때 이름이 겹치지 않게 한다.

## ⑤ 평가 경로가 실서비스 경로와 같다

평가용 파이프라인을 따로 만들지 않았다. 실제 서비스(`api/v1/chat.py`)와 **같은 함수**를 탄다.

| 단계 | 실서비스와 공유하는 함수 |
|---|---|
| 검색 | `search_hybrid()` |
| 모델 선택 | `select_optimal_model()` |
| 컨텍스트 조립 | `build_context_text()` |
| 답변 생성 | `generate_answer()` |

> 여기가 어긋나면 **실제로 돌아가지 않는 파이프라인을 측정하게 된다.**

## ⑥ 평가셋 자체가 기울어 있었다 (2026-09-14 발견)

가장 늦게, 가장 크게 드러난 문제다.

평가셋을 만들 때 쓴 프롬프트에 이런 지시가 있었다.

> *"문서 제목, 상위 경로, 팀명, 프로젝트명, 날짜 등 이 문서를 고유하게 식별할 수 있는
> 구체적인 단서 키워드를 질문 안에 반드시 자연스럽게 포함하세요"*

질문이 문서를 특정하지 못해 채점이 불가능해지는 것을 막으려는 의도였다. 부작용이 있었다.

| | 값 |
|---|---|
| 제목 단어가 질문에 **100% 포함**된 문항 | **27 / 38 (71%)** |
| 평균 포함률 | **84.7%** |

**대부분의 문항이 "제목을 알려줄 테니 그 문서를 찾아라"를 묻고 있었다.**
키워드 검색에 절대적으로 유리한 조건이고, **하이브리드 검색의 이득이 측정되지 않았다.**

대응: 같은 정답 문서를 겨냥한 채로 제목 단어만 뺀 **대조 평가셋**을 만들었다(누출 84.7% → 6.4%).

| 방식 | 제목 단어 있음 MRR | 제목 단어 없음 MRR | 낙폭 |
|---|---|---|---|
| BM25 단독 | 0.864 | 0.390 | **−55%** |
| **하이브리드** | **0.908** | **0.512** | **−44%** |

> 편향을 제거하고 나서야 하이브리드의 값어치가 보였다.
> **"최고점을 올리는 것"이 아니라 "질문이 어떻게 들어와도 덜 무너지는 것"이었다.**

## 마무리 메시지

> **AI 도입에서 가장 먼저 물어야 할 것은 "성능이 얼마인가"가 아니라
> **"그 숫자를 어떻게 쟀는가"**다.**
>
> 이 프로젝트에서 나는 판정 모델 편향, 자체 지표 편향, 조용한 채점 누락,
> 평가셋 편향을 차례로 발견했다. **네 가지 모두 측정값이 아니라 측정 방법의 문제였다.**

## 한계 (반드시 함께 말할 것)

- 38문항 1회 측정이다. **±0.02 수준 차이는 노이즈와 구분되지 않는다.**
- 대조 평가셋은 제목 단서를 빼면서 일부 문항이 모호해졌다. 절대 수치는 과소평가되며
  **방식 간 비교에만 쓴다.**
- 평가셋 문장은 LLM이 만든 것이다. **실사용 질문 분포를 대표하지 않는다.**
- `ragas_faithfulness`는 실행마다 1건씩 판정 모델이 구조화 출력을 완성하지 못해
  채점에 실패한다. 원인은 확인되지 않았다.
