# 1. 임베딩 스키마

`create_confluence_index()`의 매핑. 필드 13개가 네 가지 목적으로 갈린다.

| 목적 | 필드 | 타입 | 설명 |
|---|---|---|---|
| **검색된다** | `title` | `text` + `nori_analyzer` | 문서 제목. BM25에서 `^2.0` 가중 |
| | `text` | `text` + `nori_analyzer` | 청크 본문 |
| **벡터** | `text_vector` | `dense_vector` (1536, cosine, index:true) | OpenAI `text-embedding-3-small` |
| **거르고 찾는다** | `chunk_id` | `keyword` | 청크 고유키. ES `_id`로도 사용 |
| | `doc_id` | `keyword` | 원본 문서 id. 삭제·증분·문서 단위 묶기에 사용 |
| | `space_key` | `keyword` | Confluence Space 필터 |
| | `author` | `keyword` | 작성자 |
| | `category` | `keyword` | 대분류 (조상 페이지 기준, 예: `솔루션/개발`) |
| | `path` | `keyword` | 전체 계층 경로 |
| | `url` | `keyword` | 원문 링크. 답변에 출처로 반환 |
| **비교·정렬** | `updated_at` | `date` | 증분 재색인 비교 + 최신 문서 가산점 |
| **순서 복원** | `chunk_index` | `integer` | 청크 순서. 문서 전문을 이어붙일 때 사용 |
| | `total_chunks` | `integer` | 문서의 전체 청크 수 |

## `text`와 `keyword`를 가른 기준

이 매핑의 중심축이다.

- `text`: 분석기가 형태소로 쪼개 색인한다. "이 단어를 **포함하는가**"를 묻는 필드.
- `keyword`: 쪼개지 않고 통째로 저장한다. "이 값과 **정확히 같은가**"를 묻는 필드.

`category`를 `text`로 뒀다면 `"솔루션/개발"`이 토큰으로 쪼개져 정확 필터와 집계가 깨진다.
반대로 `text`를 `keyword`로 뒀다면 본문 전체가 한 덩어리라 검색이 불가능하다.

## 설계 판단

**날짜 표기를 펼치는 `title_search` 필드는 두었다가 제거했다 (2026-09-13).**
Nori가 `20260303`을 토큰 하나로 자르는 탓에 질문 `"2026년 3월 3일"`과 한 토큰도 겹치지 않는
문제가 있었다. 색인 시점에 제목의 날짜를 네 표기로 펼쳐 검색 전용 필드에 담았다.

**측정해보니 효과가 정확히 0이었다.** 필드 결합 방식 3종(`best_fields`/`tie_breaker`/`most_fields`)
어느 쪽에서도, 하이브리드에서도 BM25 단독에서도 소수점까지 같은 값이 나왔다.

원인은 펼치는 방향이 반대였기 때문이다.

| 펼친 표기 | 토큰화 결과 | 문서 빈도 | 기여 |
|---|---|---|---|
| `20260303` | `20260303` | 12 / 3,211 | 희소해서 점수가 크다 |
| `2026-03-03` | `2026` `03` `03` | — | 하이픈 형태는 토큰으로 남지도 않는다 |
| `2026년 3월 3일` | `2026` `년` `3` `월` `일` | 726~775 / 3,211 | **흔해서 IDF가 바닥** |

변별력 있는 토큰은 `20260303` 하나인데, **그것은 원본 `title`에 이미 들어 있고**
(`term title=20260303` -> 12건으로 동일), 질문은 그 형태를 만들어내지 않는다.
질문이 만드는 토큰은 전부 흔한 것들이라 점수 기여가 0에 가깝다.

색인 쪽에서 아무리 펼쳐도 질문 쪽이 같은 희소 토큰을 만들지 못하면 만날 수 없다.
해결하려면 질의 재작성(질문의 `"2026년 3월 3일"`을 `20260303`으로 정규화)이 필요한데,
시험해보니 38문항 중 1문항만 2위에서 1위로 올라갔다(v2 MRR 0.908 -> 0.921, v4는 변화 없음).
표본 1건은 채택 근거가 되지 않아 함께 보류했다.

**`chunk_id`를 ES `_id`로 썼다.**
같은 청크를 다시 색인하면 중복 저장이 아니라 덮어쓰기(upsert)가 된다.

**dynamic mapping을 막았다.**
인덱스가 이미 있으면 `put_mapping`으로 필드만 더한다.
그냥 두면 ES가 새 필드를 nori가 아닌 기본 분석기로 잡아 한국어가 걸리지 않는다.

**별칭 뒤에 실제 인덱스를 뒀다.**
별칭 이름으로 인덱스를 만들어버리면 갈아끼울 이름표가 사라져 무중단 재색인 경로가 막힌다.
실제 인덱스를 만든 뒤 별칭을 붙인다.

이전: 'BlackBird' -> ['BlackBird'] / 'blackbird' -> ['blackbird']   # 서로 다른 토큰
현재: 둘 다 -> ['blackbird']

| 질의 | 이전 | 현재 |
|---|---|---|
| `HashiCorp 자격증` | HashiCorp 자격증 취득현황 (41.86) | HashiCorp 자격증 취득현황 (55.05) |

### 품사 필터 부재 — 조사와 어미가 검색어가 되고 있었다

토큰 필터가 `lowercase` 하나뿐이라 조사·어미·접사가 전부 색인되고 검색 대상이 되었다.

질문 `"Jira 서버에서 Claude가 어떤 작업들을 할 수 있는지 알려줘"`의 BM25 1위는
정답이 아닌 문서였고, 그 점수 39.59를 `_explain`으로 분해하니 전부 문법 기능어에서 나왔다.

| 토큰 | 기여 | 정체 |
|---|---|---|
| `주 ㅓ` / `줘` | 8.17 / 6.77 | "알려**줘**"의 어미 |
| `알려` / `알리 어` | 4.43 / 3.59 | "**알려**줘" |
| `는지` | 3.89 | "할 수 있**는지**" |
| `어떤` | 2.82 | 의문 관형사 |
| **`jira` / `claude` / `서버`** | **0 / 0 / 0** | 그 문서에 없음 |

`줘`의 IDF가 4.624였다. 사내 문서는 대부분 격식체라 "~해줘"가 드물고, 그래서 BM25가
`줘`를 변별력 높은 단어로 취급한다. 구어체로 쓰인 문서 하나가 아무 질문에나 상위로 올라온다.

`nori_part_of_speech` 필터를 달자 그 질문의 토큰이 21개에서 12개로 줄고 정답이 1위가 됐다.

```
이전: jira 서버 에서 claude 가 어떤 작업 들 을 할 하 ᆯ 수 있 는지 알려 알리 어 줘 주 ㅓ
현재: jira 서버 claude 작업 할 하 수 있 알려 알리 줘 주
```

stoptags는 Elasticsearch 내장 `nori` 분석기의 기본 목록(18종)을 그대로 썼다.
여기에 동사·형용사(`VV`, `VA`, `VX`, `VCP`, `VCN`)까지 더한 변형도 측정했다.
한 번의 실행에서 나란히 재본 결과 hit@5는 더 높았으나 MRR은 낮았고, 차이가 노이즈 범위였다.
"쓰다", "신청하다" 같은 의미 있는 말까지 지우는 위험을 감수할 근거가 되지 않아 기본값을 택했다.

### `decompound_mode: mixed`의 효과

복합명사의 원형을 분해형과 함께 남긴다.

| 단어 | `discard` (이전 기본값) | `mixed` (현재) |
|---|---|---|
| 주차장 | `['주차', '장']` | `['주차장', '주차', '장']` |
| 출장비 | `['출장', '비']` | `['출장비', '출장', '비']` |
| 회의록 | `['회의', '록']` | `['회의록', '회의', '록']` |
| 전산실 | `['전산', '실']` | `['전산실', '전산', '실']` |
| 정보처리기사 | `['정보', '처리', '기사']` | `['정보', '처리', '기사']` (변화 없음) |

`주차장`이라는 통짜 토큰은 희소해 IDF가 높고, `주차`·`장`은 흔해 기여가 작다.
`discard`에서는 "주차장"으로 물어도 흔한 조각으로만 매칭돼 변별이 되지 않았다.
Nori 사전이 복합명사로 등록하지 않은 말(`정보처리기사`, `개인정보보호`)은 변화가 없다.

지표상 단독으로는 소폭 손해였으나(BM25 단독 기준 v2 MRR 0.921 -> 0.886)
`lowercase`와 함께 적용했을 때는 하이브리드 기준 손해가 없어 그대로 두었다.

### replicas는 코드에서 뺐다

`ELASTICSEARCH.md`가 단일 노드 기준 `0`을 정해뒀는데 코드가 값을 지정하지 않아
ES 기본값 `1`이 적용되고 있었다. 09-13에 코드에 `0`을 박았다가, 09-14에 다시 제거했다.

**단일 노드에서 yellow는 고장이 아니라 정상 동작이다.** replica shard는 primary와 같은
노드에 배치될 수 없으므로 노드가 하나면 영원히 unassigned로 남는다.

그리고 replica 수는 **배포 환경에 따라 달라지고 런타임에 바꿀 수 있는 값**이다.
애플리케이션 코드가 정할 일이 아니다. 반면 `number_of_shards`는 인덱스를 만들 때만
정할 수 있어 코드에 남겼다. 이 둘의 성격 차이가 배치 기준이다.

현재 배포는 인덱스 생성 후 운영 명령으로 0을 준다(`ELASTICSEARCH.md` 참고). 클러스터 `green`.

### 이행 방법

분석기 변경은 **기존 문서에 소급되지 않는다.** 새 인덱스를 만들고 옮겨야 한다.

1. 새 버전 인덱스를 수정된 매핑으로 생성 (09-13 `v2`, 09-14 `v3`)
2. `_reindex`로 복사 — **기존 `text_vector`를 그대로 옮기므로 임베딩 API 호출이 0이다**
   (3,211건 / 12초 / 실패 0건). `_source` 목록으로 `title_search`를 제외했다
3. 두 인덱스를 나란히 두고 측정
4. 별칭 `confluence-current`를 원자적으로 전환

`confluence-openai-v1`은 롤백용으로 남겨두고 replicas만 0으로 내렸다.

# 2. 검색 알고리즘과 평가

## 2.1 `search_hybrid()`의 6단계

질문 하나가 들어오면 다음 순서로 처리한다.

```
1. BM25로 후보 50개      ─┐
2. kNN으로 후보 50개      ─┴→ 3. 각 순위로 1/(60+순위)를 구해 합산 (RRF)
                              ↓
                          4. 최신 문서 가산점 (5분위)
                              ↓
                          5. 서로 다른 문서 5개만 선별
                              ↓
                          6. 그 5개 문서의 전문을 다시 긁어와 이어붙임
```

관련 설정값은 모두 `settings`로 빠져 있어 재색인 없이 재시작만으로 반영된다.

| 설정 | 기본값 | 뜻 |
|---|---|---|
| `RETRIEVAL_TOP_K` | `5` | 최종 컨텍스트에 넣을 **서로 다른 문서** 수 |
| `RETRIEVAL_CANDIDATE_SIZE` | `50` | BM25/kNN이 각각 가져올 재랭킹 후보 **청크** 수 |
| `RRF_K` | `60` | 순위 결합 상수. 각 리스트 순위로 `1/(RRF_K+순위)`를 계산해 더한다 |
| `RECENCY_BOOST_MAX` | `0.04` | 최신 문서 가산점. **이론상 최대 결합 점수에 대한 비율** (0이면 끔) |
| `DOC_CONTEXT_MAX_CHARS` | — | 문서 하나에서 이어붙일 최대 글자 수 |

## 2.2 단계별 판단과 근거

### 1~2단계 · 두 쿼리를 따로 실행한다

같은 요청에 `knn`과 `query`를 함께 넣으면 ES가 raw score를 그대로 더한다.
그러면 BM25(수십 단위)가 kNN(0~1)을 압도해 **사실상 BM25 단독 검색**이 된다.

`pre/` 프로젝트가 정확히 이 방식이었다. 주석에는 "벡터 3 : BM25 2"라고 적혀 있었지만
실제 점수를 대입하면 비중이 뒤집힌다.

| | 점수 | × boost | 기여 |
|---|---|---|---|
| kNN | 0.725 | × 3.0 | 2.18 (7%) |
| BM25 | 14.93 | × 2.0 | 29.86 (**93%**) |

BM25 쿼리는 `["title^2.0", "text"]`에 `best_fields`를 쓴다.
사내 업무 문서는 제목이 내용을 잘 요약하는 편이라 제목에 2배 가중치를 준다.

### 3단계 · RRF (Reciprocal Rank Fusion)

```python
bm25_rrf = _rrf_scores(bm25_hits)     # chunk_id -> 1/(K + 순위)
knn_rrf  = _rrf_scores(knn_hits)
...
combined_score = bm25_rrf.get(chunk_id, 0.0) + knn_rrf.get(chunk_id, 0.0)
```

**점수를 쓰지 않고 순위만 쓴다.** 각 리스트에서 몇 등이었는지로 `1/(K+순위)`를 구해 더한다.
`K=60` 기준 1위 `1/61`, 2위 `1/62`, 50위 `1/110`.
양쪽 리스트에 모두 든 청크는 두 번 더해지므로 자연히 위로 온다.

**이론상 최대 점수**는 양쪽 모두 1위일 때의 `2/(K+1) = 0.0328`이다(`rrf_max_score()`).
최신성 가산점의 기준으로 쓴다.

#### min-max 정규화에서 바꾼 이유 (2026-09-14)

이전에는 각 리스트를 0~1로 min-max 정규화한 뒤 4:6으로 가중평균했다. 두 가지 문제가 있었다.

**① 폭이 좁은 리스트의 미세한 차이가 부풀려진다.**
정규화는 점수를 "그 리스트의 전체 폭 대비 비율"로 바꾼다. 실측:

| | 1위 | 2위 | 전체 폭 | 1↔2위 실제 차 | 정규화 후 차이 |
|---|---|---|---|---|---|
| kNN | 0.7440 | 0.7060 | **0.0922** | 0.0380 (폭의 41%) | **0.4122** |

코사인 0.744와 0.706은 의미상 거의 같은데 정규화가 "1등과 한참 아래"로 만든다.
kNN 후보 50건이 늘 0.65~0.74의 좁은 구간에 몰려 있어 이 왜곡이 항상 일어난다.

**② min/max가 바뀌면 같은 문서의 점수가 바뀐다.**
색인이 커지면 BM25의 IDF가, 임베딩 모델을 바꾸면 코사인 분포가 이동한다.
실제로 코퍼스가 2,979 → 3,211청크로 늘면서 `PORTFOLIO_SLIDES.md`의 예시가 재현되지 않았다.

순위는 다른 문서의 점수와 무관하므로 두 문제가 모두 사라진다.

RRF는 Elasticsearch, OpenSearch, Weaviate, Qdrant, Azure AI Search가 공통으로 쓰는 표준 방식이다.
ES의 `retriever.rrf`는 basic 라이선스에서 막혀 있으나(실측 확인:
`current license is non-compliant for [Reciprocal Rank Fusion (RRF)]`),
**두 리스트를 이미 따로 받아 직접 합치고 있으므로 ES 기능이 없어도 된다.**
2026-09-01 기록에도 "정석은 RRF이나 ES basic 라이선스가 지원하지 않는다.
필요해지면 순위 기반으로 직접 구현할 것"이라고 적어두었고, 그 계획을 이행한 것이다.

#### 가중치를 없앤 이유

RRF에도 가중치를 줄 수 있다(`Σ w/(K+순위)`). 측정해보니 주지 않는 쪽이 나았다.

| | v4 hit@5 | v4 MRR |
|---|---|---|
| 동일 가중 | **0.763** | **0.549** |
| BM25 0.4 : kNN 0.6 | 0.737 | 0.531 |

min-max 시절의 `4:6`은 "kNN을 더 믿는다"는 뜻이면서 정규화 왜곡을 보정하는 성격도 있었다.
RRF에는 왜곡이 없으므로 가중치는 순수하게 "어느 엔진의 순위를 더 믿을까"가 되는데,
그 답이 질문마다 달라 고정 가중치가 오히려 방해가 된다.

#### `K` 값

| `K` | 1위 | 50위 | 1위÷50위 |
|---|---|---|---|
| 10 | 0.09091 | 0.01667 | 5.45배 |
| **60** | 0.01639 | 0.00909 | **1.80배** |
| 200 | 0.00498 | 0.00400 | 1.24배 |

`K`가 작으면 상위권이 유리해 한 엔진의 확신을 존중하고, 크면 평평해져 양쪽 합의를 중시한다.
60은 RRF 원 논문의 기본값이다. 실측에서 `K=10`과 `K=60`의 결과가 같아 표준값을 따랐다.

#### 트레이드오프

RRF는 "압도적 1위"를 표현하지 못한다. BM25가 완벽히 일치하는 문서를 찾아도 2위와
`1/61 − 1/62 = 0.00026` 차이일 뿐이다. **키워드가 잘 맞는 질문에서는 이득이 없다.**
실측에서 v2 원본(질문에 문서 제목이 들어 있음)은 두 방식이 완전히 동일했고,
v4(제목 단어를 뺀 대조군)에서만 갈렸다.

#### 결합 방식 변천

| 시점 | 결합 방식 | 비고 |
|---|---|---|
| 2026-08-21 | 정규화 + 3:2 | BM25 우세. 직접 결합에서 정규화 도입 |
| 2026-08-21 (같은 날) | 정규화 + 3:7 | kNN 우세로 뒤집음 |
| 2026-09-01 | 정규화 + 4:6 | RAGAS 지표를 보며 조정 |
| **2026-09-14** | **RRF (K=60), 가중치 없음** | **순위 기반으로 전환** |

### 한쪽 리스트에만 든 청크의 처리

한쪽 후보 풀에 없는 청크는 그쪽 기여가 없다. 더하기이므로 양쪽에 든 청크가 유리하다.

| 상황 | RRF 점수 | (참고) 이전 min-max 방식 |
|---|---|---|
| 양쪽 1위 | `2/61 = 0.0328` | 1.00 |
| 양쪽 10위 | `2/70 = 0.0286` | 0.80 |
| BM25 1위, kNN 밖 | `1/61 = 0.0164` | 0.40 |
| kNN 20위, BM25 밖 | `1/80 = 0.0125` | 0.30 |

**"양쪽이 인정한 문서가 위로 온다"는 성질은 두 방식이 같다.** 강도가 다르다.
RRF에서는 `BM25 1위 + kNN 밖`(0.0164)이 `양쪽 10위`(0.0286)보다 아래다.

실측(질문 3개 기준):

| | 청크 수 | 최고 순위 |
|---|---|---|
| 양쪽에 든 청크 | 12~15개 | **1위** (상위 10 중 8~10개) |
| kNN에만 든 청크 | 35~38개 | 7~11위 |
| BM25에만 든 청크 | 35~38개 | 12~18위 |

후보 합집합이 85~87개인데 겹치는 것은 15% 남짓이고, 최종 선택되는 5개는 거의 전부 그 교집합에서 나온다.

> **설계 의도는 "한쪽이 놓친 것을 다른 쪽이 보완"이었지만, 실제 동작은 "양쪽이 합의한 문서 우선"에 가깝다.**

`CANDIDATE_SIZE`를 40에서 50으로 올린 것은 이 문제의 완화책이다. 풀이 클수록 겹칠 확률이 오른다.
다만 0으로 채우는 성질 자체는 남는다.

### kNN 점수에는 변별력이 거의 없다 (실측 · RRF로 바꾼 근거)

질의 `"휴가 신청 절차"` 기준, 후보 50건의 점수 분포:

| | 최고 | 최저 | 폭 |
|---|---|---|---|
| BM25 | 14.93 | 7.02 | **7.91** |
| kNN | 0.725 | 0.665 | **0.0601** |

kNN은 1등과 50등의 코사인 유사도가 사실상 같다.
그런데 min-max 정규화는 이 0.06을 0~1로 늘린다. 결과적으로

- BM25의 **의미 있는 7.91 폭** → 0~1로 **압축**
- kNN의 **거의 노이즈인 0.06 폭** → 0~1로 **증폭**

min-max 정규화를 쓰던 시절의 `4:6`은 겉보기와 달리 "변별력 있는 신호를 눌러 담고
변별력 없는 신호를 부풀린 뒤 6할을 주는" 구조에 가까웠다. RRF로 바꾸면서 해소됐다.

### 4단계 · 최신 문서 가산점 (`_apply_recency_bonus`)

후보를 `updated_at` 기준 최신순 5등분해 최신 그룹부터 차등 가산한다.
절대 시각이 아니라 **후보 풀 안의 상대 순위**로 나눈다.

**값은 절대값이 아니라 이론상 최대 결합 점수(`2/(K+1) = 0.0328`)에 대한 비율이다.**
`RECENCY_BOOST_MAX = 0.04`는 "최대치의 4%"를 뜻한다.

비율로 둔 이유: 결합 방식을 바꾸면 점수 범위가 통째로 달라진다. min-max 정규화는 0~1이었고
RRF(K=60)는 0~0.0328이다. 절대값 0.04를 그대로 물려줬다면 **가산점이 점수를 압도해
사실상 최신순 정렬이 됐을 것이다.** 이 함정은 2026-09-02에 이미 기록돼 있었고,
2026-09-14 RRF 전환 때 비율 방식으로 고쳐 피했다.

**비율별 실측 (2026-09-14, RRF 기준)**

| 가산점 | v2 MRR | v4 MRR |
|---|---|---|
| 끔 (0%) | 0.908 | 0.549 |
| **최대치의 4%** | **0.908** | **0.560** |
| 최대치의 10% | 0.846 | 0.496 |
| 최대치의 25% | **0.668** | 0.478 |

4%는 무해하거나 소폭 이득이고, 10%부터 무너진다. 25%는 "사실상 최신순 정렬"이 되는 지점이다.

min-max 시절 측정(2026-09-02)에서는 `retrieval_hit`이 전혀 변하지 않았고 상위 5개 구성은
40건 중 10건에서 바뀌었는데 **전부 5순위 한 칸만 교체**됐다. 정답 문서를 밀어낸 사례는 0건이다.
`context_precision`은 0.835 → 0.800으로 0.035 낮아졌다. 관련성이 아니라 최신성으로 문서를
올리는 대가다.

> 근거는 지표가 아니라 **"사내 문서에서 최신본을 우선하는 것이 타당한 기본 동작"**이라는 판단이다.
> RRF 전환 후 v4에서 소폭 이득(+0.011)이 관찰됐으나 38문항 1회 측정이라 확정하지 않는다.

한계: `updated_at`은 Confluence 최종 수정 시각이라 "문서 내용의 날짜"와 다르다.
오래된 회의록에 오타 하나만 고쳐도 최신이 된다.

### 5단계 · 청크가 아니라 "서로 다른 문서" 5개

같은 문서의 청크가 상위권을 독점하면 다른 관련 문서가 밀려난다.
2026-08-21 실측: MCP 문서 관련 질문에서 `top_k=3`이 전부 "설치 방법" 청크로 채워지고
정작 답이 있는 "기능 목록" 청크가 들어오지 못한 사례를 확인했다.

### 6단계 · 문서 전문 확장 (`_fetch_full_doc_texts`)

검색으로 문서가 한 번 걸리면, 그 문서의 청크를 `chunk_index` 순으로 이어붙여 컨텍스트에 넣는다.
대표로 매칭된 청크 하나만 넣으면 정작 답이 있는 다른 청크가 빠지기 때문이다.

- 문서마다 따로 조회하면 `top_k`에 비례해 왕복이 늘어난다(N+1).
  `terms` 쿼리 **하나**로 모두 가져와 파이썬에서 `doc_id`별로 나눈다.
- `_MAX_CHUNKS_PER_DOC = 50`으로 비정상적으로 긴 문서가 요청을 부풀리는 것을 막는다.
- 조회에 실패한 문서는 매칭된 청크 원문을 그대로 둔다 (컨텍스트가 비는 것보다 낫다).

### 성능 관련

- `_SEARCH_SOURCE_FIELDS`로 받을 필드를 지정한다. 지정하지 않으면 1536차원 `text_vector`까지
  딸려와 후보 100청크 기준 요청당 수 MB를 전송·파싱하고 그대로 버린다.
- `search_hybrid_async()`는 동기 함수를 `asyncio.to_thread`로 감싼 래퍼다.
  FastAPI 메인 이벤트 루프가 ES 응답을 기다리며 막히지 않게 한다 (2026-08-23 비동기 전환).
- `_self_check()`는 ES 없이 검증 가능한 순수 계산만 확인한다. `python -m app.retrieval.es_client`.

## 2.3 평가 데이터셋

검색 지표는 정답 문서 id만 있으면 계산되므로 LLM 판정 없이 잴 수 있다.

| 지표 | 뜻 |
|---|---|
| `retrieval_hit` (hit@5) | 정답 문서가 상위 5건 안에 들었는가 (0 또는 1) |
| `retrieval_mrr` | 정답 문서의 순위 역수 (1등 1.0 / 2등 0.5 / 3등 0.33 / 못 찾음 0) |

`hit@5`만으로는 정답이 1등이든 5등이든 구분하지 못한다.
실제로 결합 방식을 바꿔가며 재보면 `hit@5`는 전부 같은데 MRR만 갈리는 경우가 많아 MRR을 함께 본다.

채점 대상은 **45문항 중 38문항**이다.
`known_gap`(본문 없는 문서를 겨냥해 ES에 존재하지 않음)과 out-of-domain 문항은 제외한다.
검색이 못 찾는 것이 정상이라 채점하면 구조적으로 0점이 되어 지표를 왜곡한다.

### ⚠️ v2 평가셋은 BM25 쪽으로 기울어 있다

`generate_dataset.py`의 질문 생성 프롬프트가 이렇게 지시한다.

> 문서 제목, 상위 경로, 팀명, 프로젝트명, 날짜 등 **이 문서를 고유하게 식별할 수 있는
> 구체적인 단서 키워드를 질문 안에 반드시 자연스럽게 포함**하세요

의도는 "질문이 문서를 특정하지 못해 채점이 불가능해지는 것"을 막는 것이었고 그 목적에는 맞다.
부작용으로 질문이 정답 문서의 제목을 그대로 담게 됐다.

| | 값 |
|---|---|
| 제목 단어가 질문에 100% 포함된 문항 | **27 / 38 (71%)** |
| 절반 이상 포함된 문항 | 34 / 38 |
| 평균 포함률 | **84.7%** |

이 조건은 키워드 검색의 홈그라운드다. 실제로 BM25 단독이 하이브리드보다 MRR이 높다.

| 방식 | hit@5 | MRR |
|---|---|---|
| 하이브리드 (RRF) | 0.974 | 0.908 |
| **BM25 단독** | 0.947 | **0.864** |
| kNN 단독 | 0.921 | 0.812 |

(2026-09-13 분석기 수정 전에는 BM25 단독이 0.974 / **0.921**로 하이브리드를 앞섰다.
수정 후 역전됐으나, 평가셋이 기울어 있다는 사실 자체는 그대로다.)

> **이 평가셋으로는 하이브리드의 이득을 측정할 수 없다.**
> 이득이 없다는 뜻이 아니라, 이득이 드러날 조건의 문항이 거의 없다는 뜻이다.

### v4 paraphrase — 편향을 뺀 평가셋

v2의 채점 문항 38개를 **같은 정답 문서에 대해** 다시 썼다.
제목·경로·팀명·프로젝트명을 쓰지 말고 동의어와 구어체로 묻게 해
제목 단어 누출을 **84.7% → 6.4%**로 낮췄다.
정답 문서를 고정했으므로 질문 표현 외의 변수는 통제된다.

- 생성기: `evaluation/generate_paraphrase_dataset.py`
- 스냅샷: `evaluation/paraphrase_dataset_items.py` (`qa-v4-para-001` ~)
- 측정: `evaluation/compare_fusion.py`

### 측정 결과 — 하이브리드는 평균이 아니라 바닥을 받친다

| 방식 | 제목 단어 있음 (v2) | 제목 단어 없음 (v4) | 낙폭 |
|---|---|---|---|
| BM25 단독 | MRR **0.864** | MRR **0.390** | **−55%** |
| 하이브리드 (RRF) | MRR 0.908 | MRR **0.560** | **−38%** |
| kNN 단독 | MRR 0.812 | MRR **0.501** | **−38%** |

hit@5도 같은 방향이다.

| 방식 | v2 | v4 |
|---|---|---|
| BM25 단독 | 0.947 | **0.605** |
| 하이브리드 | 0.974 | **0.763** |
| kNN 단독 | 0.921 | 0.605 |

문항별 직접 대결(MRR 기준)은 방향이 뒤집힌다.

| | 하이브리드 승 | BM25 승 | 동점 |
|---|---|---|---|
| v2 (제목 단어 있음) | **5** | 3 | 30 |
| v4 (제목 단어 없음) | **16** | 2 | 20 |

> **결론: 하이브리드의 값어치는 평균 성능이 아니라 최악의 경우 방어에 있다.**
> BM25는 질문에 문서 제목 단어가 있으면 강하지만 없으면 절반 아래로 떨어진다(−55%).
> 하이브리드는 같은 조건에서 −38%로 덜 무너진다.
> 질문 표현을 통제할 수 없는 사내 챗봇에서는 최고점보다 이 성질이 중요하다.

### 슬롯 배분 방식 — 검토 후 미채택

점수를 섞지 않고 각 리스트에서 정해진 수만큼 가져오는 방식(kNN 3 + BM25 2 등).
한쪽 리스트에만 걸린 문서도 자리가 보장되므로 위의 "0으로 채우기" 성질을 피할 수 있다.

| 문항 집합 | 하이브리드 MRR | 슬롯(kNN3+BM25 2) MRR |
|---|---|---|
| v2 | **0.908** | 0.827 |
| v4 | **0.560** | 0.525 |

RRF로 바꾼 뒤로는 v4에서도 하이브리드가 앞선다(+0.035). v2에서는 여전히 크게 이긴다(+0.081).
또한 슬롯은 **질문과 무관하게 자리를 고정**하므로, 질문마다 어느 쪽이 더 확신을 갖는지를 반영하지 못한다.
실제 사용자 질문의 분포를 모르는 상태에서 한쪽에 치우친 집합 하나로 결정하지 않는다.

**현재 방식을 유지한다.** 실사용 질문 로그가 쌓이면 `compare_fusion.py`로 다시 판단한다.

### 평가의 한계

- v4는 제목 단서를 빼면서 일부 문항이 모호해졌다(정답 문서가 유일하지 않을 수 있다).
  절대 수치는 과소평가되며 방식 간 비교에만 쓴다.
- 38문항 1회 측정이다. 낙폭의 방향은 분명하지만 값 자체는 정밀하지 않다.
- v4는 실제 사용자 질문이 아니라 LLM이 다시 쓴 문장이다.
- 필드 결합 방식 3종(`best_fields` / `tie_breaker` / `most_fields`)은 `hit@5`로 구분되지 않고
  MRR만 갈렸다. 38문항에서 1~2건 차이라 우열을 확정하지 않고 현재 방식을 유지했다.

### 남은 검색 실패 1건

2. 색인 시 날짜를 펼쳐도 `년/월/일`은 모든 날짜 문서에 흔해 IDF가 바닥이라 기여하지 못함
   (이 때문에 `title_search` 필드를 만들었다가 효과가 0으로 측정돼 제거했다. 위 1절 참조)

# 3. 증분·삭제 처리

바뀐 문서만 다시 넣고 사라진 문서는 지운다. 3단으로 나뉜다.

## 3단 구성

### 1단 · 건너뛰기 (비용)

```python
indexed_updated_ats = get_indexed_updated_ats(doc_ids)
target_pages = [p for p in pages
                if indexed_updated_ats.get(p["id"]) != p.get("last_updated")]
```

ES에 저장된 `updated_at`과 Confluence의 최신 값을 비교해 **다른 것만** 재색인한다.
`--force`를 주면 비교를 건너뛰고 전부 재색인한다.

`get_indexed_updated_ats()`는 **집계(aggregation)**를 쓴다.

```python
"size": 0,
"aggs": {"by_doc": {"terms": {"field": "doc_id", ...},
                    "aggs": {"latest_updated_at": {"max": {"field": "updated_at"}}}}}
```

한 문서가 여러 청크로 쪼개져 있지만 `updated_at`은 문서 단위로 동일하므로
`doc_id`로 묶어 대표값 하나씩만 모으면 된다. `"size": 0`이라 문서 본문은 받아오지 않는다.

> 이것이 아끼는 것은 ES 조회가 아니라 **임베딩 API 호출**이다.
> 재색인 비용의 대부분이 거기 있다.

비교는 문자열 직접 비교다. 형식이 일치하는 것을 확인했다.

```
ES _source 저장값        : '2026-01-29T01:54:46.115Z'
집계 value_as_string     : '2026-01-29T01:54:46.115Z'
```

형식이 어긋나면 모든 문서가 매번 변경된 것으로 판정되어 조용히 전체 재색인이 돈다.
`updated_at` 매핑이나 Confluence 응답 형식을 바꿀 때 확인이 필요한 지점이다.

### 2단 · 지우고 다시 쓰기 (정합성)

```python
delete_documents_by_ids(target_doc_ids)   # 색인 '전에' 실행
...
index_document_chunks(all_chunks, vectors=vectors)
```

**`chunk_id`를 `_id`로 쓰는 upsert만으로는 부족하다.**
문서가 짧아져 청크가 5개 → 3개가 되면 `chunk_4`, `chunk_5`는 덮어쓸 대상이 없어
**이전 버전 내용이 그대로 남는다**(고아 청크).
그래서 색인 전에 대상 문서의 기존 청크를 먼저 지운다.

이 패턴은 `pre/` 프로젝트의 `delete_page_vectors()`에서 가져왔다.

### 3단 · 삭제 동기화 (2026-09-14 구현)

Confluence의 전체 문서 id와 색인된 전체 `doc_id`를 비교해, **색인에만 남아 있는 문서**를 지운다.
원본이 사라진 뒤에도 챗봇이 그 문서를 근거로 답하는 것을 막는다.

```python
live_ids    = set(fetch_all_page_ids())        # Confluence에 현재 있는 문서
indexed_ids = set(get_all_indexed_doc_ids())   # 색인에 있는 문서
stale_ids   = indexed_ids - live_ids           # 색인에만 있는 것 = 삭제된 것
delete_documents_by_ids(list(stale_ids))
```

2026-09-14 이전에는 `fetch_all_page_ids()`가 이 목적으로 작성돼 있었으나 어디에도
연결되어 있지 않았다. ES 쪽 목록을 가져오는 함수도 없었다. 두 가지를 채워 연결했다.

**세 가지 안전장치를 뒀다.** 검색 데이터를 지우는 동작이라 잘못 돌면 되돌리기 어렵다.

| 장치 | 이유 |
|---|---|
| 전체 스페이스 실행에서만 동작 (`--limit`/`--category`면 건너뜀) | 일부만 수집한 목록으로 비교하면 **수집 범위 밖 문서가 전부 삭제 대상**이 된다 |
| `fetch_all_page_ids()`가 실패 시 예외를 올림 | 기존에는 예외를 삼키고 부분 목록을 돌려줬다. 그대로 쓰면 "나머지는 삭제된 문서"로 오해한다 |
| 목록이 비면 건너뜀 | 빈 목록은 "전부 삭제"를 뜻하게 된다 |

`--no-prune`으로 이 단계만 끌 수 있다.

**본문이 없어 청크가 0개인 문서는 이 비교에 걸리지 않는다.** 애초에 색인되지 않으므로
`indexed_ids`에 없기 때문이다. 실측(2026-09-14): Confluence 651건 / 색인 583건,
차이 68건은 본문 없는 문서 57건 + 마지막 색인 이후 새로 생긴 11건이며 삭제 대상은 0건이었다.

## 전체 재색인 경로 (별칭)

일상적인 증분 색인과 별개로, 임베딩 모델이나 차원이 바뀌어 **전체 재구축**이 필요할 때의 경로다.

1. 새 버전 인덱스를 만들어 채운다
2. 별칭만 옮긴다
3. 문제가 생기면 별칭을 되돌린다

재색인 동안 검색이 끊기지 않고, 롤백이 별칭 전환 하나로 끝난다.
별칭이 없으면 같은 작업에 `.env` 수정과 컨테이너 재생성이 필요하고 그 사이 검색이 멈춘다.
