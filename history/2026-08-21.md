## 4. Langfuse 연동 + RAG 품질 진단/수정 (같은 날 이어서 진행)

### 4-1. Langfuse 연동 자체를 살림
- 계기: "Langfuse 연동해서 테스트 데이터셋 만들고 QA 해줄 수 있어?"
- 발견: `chat.py`에 `@observe` 트레이싱 코드는 이미 있었지만 실제로는 죽어있었음.
  1. `langfuse` 패키지가 `requirements.txt`에 없어 import가 항상 실패 → no-op으로만 동작.
  2. `.env`에 `LANGFUSE_BASE_URL`로 적혀있어 `config.py`가 읽는 `LANGFUSE_HOST`와 이름이 안 맞음 (리전이 `jp.cloud.langfuse.com`인데 기본값 `cloud.langfuse.com`으로 나갈 뻔함).
  3. `main.py`에서 Langfuse env 주입이 `chat_router` import보다 **뒤에** 있어서, 라우터 로드 시점에 SDK가 키 없이 초기화될 위험.
  4. 최신 `langfuse` 패키지는 v3(OTel 기반)라 기존 코드가 쓰던 `langfuse.decorators`(v2 API)가 아예 없는 모듈이 됨.
- 수정: `.env` 변수명 정리, `main.py` 주입 순서 수정, `chat.py`를 v3 API(`from langfuse import observe, get_client`)로 마이그레이션, `requirements.txt`에 `langfuse>=3.7.0` 추가.
- 검증: `auth_check()` 통과 + 스모크 트레이스가 실제 프로젝트(`cmt0xmxjm...`)에 찍히는 것까지 API로 직접 확인.

### 4-2. QA 데이터셋 + 평가 하네스 구축 (`ai-server/evaluation/`)
- `dataset_items.py`: 실제 ES 인덱스 문서를 근거로 만든 16개 질문 (일반 정답 문항 12개 + Confluence "database" 임베드라 본문이 없는 문서를 겨냥한 known-gap 문항 2개 + 관련 문서가 아예 없는 out-of-domain 문항 2개). 각 아이템에 `expected_doc_ids`를 같이 넣어서 "검색이 못 찾은 건지 답변이 틀린 건지"를 분리 채점할 수 있게 설계.
- `push_dataset.py`: Langfuse Dataset(`confluence-rag-qa-v1`)에 id 고정 업서트.
- `run_qa.py`: `dataset.run_experiment()`로 실제 파이프라인(검색+생성)을 돌리고 3개 지표를 따로 채점.
  - `retrieval_hit`: ES 하이브리드 검색이 top_k 안에 정답 문서를 찾았는가
  - `answer_faithfulness`: 답변이 검색된 컨텍스트에 근거하는가 (LLM judge)
  - `answer_correctness`: 최종 답변이 기대 답변과 일치하는가 (LLM judge)
  - 세 점수 조합으로 "검색 실패 / 컨텍스트는 맞는데 LLM이 무시함 / 컨텍스트도 맞고 충실한데 추론이 틀림"을 자동 진단.

### 4-3. 하이브리드 검색 스코어 결합 버그 발견 및 수정
- 첫 QA 실행에서 `retrieval_hit` 0.857 (16개 중 2개 실패, 둘 다 "엔드포인트"(한글) 질문 — 정답 문서 제목은 "Endpoint"(영문)).
- 원인 추적: `search_hybrid()`가 ES `_search` 하나에 `query`(BM25)와 `knn`을 같이 넣는데, ES가 최종 `_score`를 사실상 BM25 원시 점수로만 결정하고 있었음. 실측: BM25 원시 점수(7~12대) vs kNN 코사인 유사도(0~1대) — 스케일 차이 때문에 kNN 기여가 사실상 0. "BM25+kNN 결합" 결과가 "BM25만" 결과와 완전히 동일했음.
- 표준 해법인 ES `retriever.rrf`도 시도했으나 `현재 라이선스(basic)가 RRF에 비호환`으로 거부됨.
- 최종 수정 (`es_client.py`): BM25 쿼리와 kNN 쿼리를 각각 따로 실행 → chunk_id 기준 0~1 min-max 정규화 → **BM25:kNN = 3:2 가중합**으로 재랭킹 (원래 의도했던 가중치를 원시 스케일이 아니라 정규화된 스케일에 적용).
- 재검증: `retrieval_hit` 0.857→**1.000**, `answer_correctness` 0.863→**0.975**, 실패 진단 0건.

### 4-4. Confluence "Databases" 임베드 콘텐츠는 API 한계로 확인 (수정 보류)
- 프로젝트 산출물 문서 중 일부(`03.설계_구성 아키텍처` 등)가 본문 없이 링크만 파싱되는 문제를 재확인.
- Confluence REST API(`/rest/api/content`, v1/v2 모두)로 원본 `body.storage.value`를 직접 찍어보니, 애초에 `<a href=".../database/ID" data-card-appearance="embed">` 카드 링크만 들어있고 실제 표 데이터(행)는 응답에 없음. `/api/v2/databases/{id}`로 직접 조회해도 메타데이터(제목/parentId 등)만 나오고 행 데이터는 어떤 공개 API로도 안 나옴.
- 결론: 파서/ingest 버그가 아니라 **Confluence Databases 기능 자체가 REST API로 행 데이터를 노출하지 않는 플랫폼 한계**. 대응은 보류(알려진 갭으로만 관리), QA 데이터셋의 known-gap 문항으로 "봇이 헛소리 안 하고 정직하게 모른다고 답하는지"만 확인.

### 4-5. 메타데이터(category/path/primary_contributor) 공백 원인 발견
- ES 인덱스의 `category`/`path`/`primary_contributor` 필드가 전부(83/83 청크) 비어있는 걸 발견.
- 원인: `fetch_pages_with_category()`/`get_primary_contributor()` 자체는 지금 정상 동작하는데, `ingest.py`의 증분 색인 로직이 Confluence 문서의 `last_updated`가 안 바뀌면 재색인을 건너뜀. 이 메타데이터를 채우는 코드가 나중에 추가된 뒤로 해당 문서들이 한 번도 안 바뀌어서, 옛날(필드 없던 시절) 색인 상태가 계속 남아있었던 것.

### 4-6. 전체 재색인 중 인프라 장애 발생 → 원인 규명 → 복구
- `--force`로 전체(575문서) 재색인 시도 → 임베딩 2719개 전부 생성 성공했으나 마지막 ES bulk 색인 단계에서 `Connection timed out`. 재색인 전에 기존 83개 청크를 먼저 지우는 로직 때문에 **인덱스가 완전히 비어버림** (`count: 0`).
- 1차 원인: ES 클라이언트 기본 요청 타임아웃(10s)이 1536차원 벡터 포함 대량 bulk에 비해 너무 짧음. `get_es_client()`에 `request_timeout=60, max_retries=3, retry_on_timeout=True` 추가, `index_document_chunks()`의 bulk `chunk_size`를 500→200으로 축소.
- 재시도했는데도 또 타임아웃 → `_cluster/health` 확인 결과 `task_max_waiting_in_queue_millis`가 약 40시간(!)에 달함. 근본 원인: **서버 디스크 사용량 98%** (`/`: 44G 중 43G 사용, 여유 1.2GB) → ES flood-stage watermark를 넘어서 클러스터가 쓰기를 막고 있었고, 그 여파로 마스터 노드의 클러스터 상태 처리 큐 자체가 하루 넘게 정체돼 있었음 (`cluster_reroute(disk threshold monitor)` 태스크가 원흉으로 추정).
- 디스크 원인: `/root` 하나가 30GB. `/root/.cache/pip`(7.8G), `/root/.cache/JetBrains`(5.9G), `/root/.npm`(1.7G), `/root/.gradle/caches`(1.5G) 등 전부 재생성 가능한 캐시였음 (VSCode/Cursor 서버 파일은 현재 접속 세션이라 안 건드림). 총 ~17GB 정리 → 디스크 98%→73%.
- 디스크를 비웠는데도 클러스터 상태 처리 큐는 안 풀림(설정 변경 요청조차 30초 타임아웃) → `docker compose restart elasticsearch`로 컨테이너 재시작 → pending task 큐 정상화(대기시간 40시간→0). `es_data`가 named volume(`es_data:/usr/share/elasticsearch/data`)이라 재시작해도 데이터 유실 없음.
- 위 수정들(타임아웃/배치크기/디스크/클러스터) 다 반영 후 전체 재색인 재실행 → **575문서 → 2719청크 색인 성공**. `category`/`path`/`primary_contributor` 메타데이터도 이번엔 정상적으로 채워진 것까지 확인.

### 4-7. LiteLLM 게이트웨이의 이중 Langfuse 로깅 발견 (부분 해결, 완전 연결은 보류)
- Langfuse UI에서 `litellm-acompletion`/`litellm-aembedding`이라는, 우리 앱 트레이스와 무관한 독립 트레이스가 보이는 걸 발견.
- 원인: `litellm/config.yaml`에 `success_callback: ["langfuse"]`가 이미 설정돼 있어 LiteLLM 게이트웨이 자체가 별도로 Langfuse에 직접 로깅 중. 이 트레이스는 `sessionId: null`, `parentObservationId: null`로 우리 세션/검색 결과/QA 점수와 전혀 연결이 안 됨.
- 추가 확인: 오늘 새로 발급한 Langfuse 키를 `.env`에 넣었지만 `kg-litellm` 컨테이너는 그 전부터 떠있던 거라 `printenv`로 확인해보니 `LANGFUSE_*` 변수가 아예 없었음 (`env_file`은 컨테이너 생성 시점에만 반영됨). `docker compose up -d litellm`으로 재생성해서 해결, 로그로 `Initialized Success Callbacks - ['langfuse']` 확인.
- LiteLLM 요청에 `metadata: {"existing_trace_id": ...}`를 실어서 우리 트레이스에 자식으로 붙이는 방법을 시도했으나, 실험 결과 기대한 trace_id로 안 붙음 (LiteLLM 버전별로 연결 파라미터가 자주 바뀌는 편). 이 부분은 코드 변경 없이 실험만 하다 보류 — 실제 파일(`litellm_client.py`, `chat.py`)엔 손 안 댐, `git status` 깨끗함.

## 5. QA 데이터셋 확장(16→67개) + 하이브리드 검색 추가 튜닝 (같은 날, 더 이어서 진행)

### 5-1. 프롬프트를 별도 파일로 분리
- `ai-server/app/llm/prompts.py` 신설, `RAG_SYSTEM_PROMPT` 상수로 분리. Confluence 데이터베이스 임베드 링크만 있고 실제 본문이 없는 문서를 만나면 "확인 불가, 링크 참고"라고 안내하도록 프롬프트에 규칙 추가 (4-4의 known-gap 문제 완화).

### 5-2. Codex에게 데이터셋 확장을 맡겨봤으나 보류 → 자동 생성 스크립트로 전환
- 31→575개 문서로 커진 인덱스에 맞게 QA 데이터셋을 40~60문항으로 늘리는 작업을 Codex에 위임하려 했으나 사용자가 "힘들다"는 판단으로 보류.
- 대신 `ai-server/evaluation/generate_dataset.py` 작성: ES에서 카테고리별로 문서를 샘플링(카테고리 비중 대략 반영, 14개 카테고리)해서, 문서 원문을 LLM(`gpt-4o-mini`)에 주고 그 내용에만 근거한 질문/답변 쌍을 자동 생성. 사람이 답을 지어내지 않고 실제 원문에서 뽑으므로 골든라벨 신뢰도가 상대적으로 높음.
- 51개 문항 생성 성공 → 기존 16개 + 신규 51개 = **총 67개 문항**으로 `dataset_items.py` 확장.

### 5-3. 67개로 처음 돌렸을 때 retrieval_hit 급락 (0.938→0.631 아님, 1.000→0.631) → 원인 두 갈래로 분리
- 31개 문서 기준으로 만들었던 기존 16개 문항까지 포함해서 재검증했더니 `retrieval_hit`이 1.000→0.631로 급락.
- 원인 A (버그 아님, 데이터셋 노후화): 인덱스가 575개로 커지면서, 기존 문항의 골든 doc_id보다 **더 적합한 전용 문서가 새로 생긴 경우**가 있었음 (예: `qa-002` "삼성 SDS FabriX 파트너 계약" — 예전엔 `회사 연혁`에서만 한 줄 언급됐는데, 지금은 `Samsung SDS FabriX 파트너사 실전 활용 교육`이라는 전용 문서가 있음). 검색은 오히려 더 잘한 케이스. → 사용자 판단으로 **백로그로 남기고 지금은 손 안 댐**.
- 원인 B (진짜 검색 회귀): 후보 풀 크기(`candidate_size = max(top_k*5, 20)`)가 31개 문서 규모에 맞춰진 값이라 575개 규모에서는 너무 작아서, 진짜 정답 문서가 후보에도 못 들어가는 경우 발생 (`qa-006` vLLM 엔드포인트 질문 등).
- 사용자 지시로 BM25:kNN 가중치를 3:2 → **5:5**로 조정 → `retrieval_hit` 0.631→0.662로 소폭 개선 (원인 B는 일부 완화, 원인 A는 그대로 남음 — 서로 다른 문제라 하나의 파라미터로 둘 다 못 고침).

### 5-4. 자동생성 문항 대량 실패의 진짜 원인: 질문이 모호함 (검색 파라미터 문제 아님)
- 실패 항목 대부분이 신규 51개 문항에 몰려있는 걸 보고 원인 재조사.
- 원인: 생성 프롬프트가 "이 문서는 어떤 용도인가요?", "주간 미팅 일시는 언제인가요?" 같은, **그 문서를 특정할 단서가 질문 안에 전혀 없는 질문**을 다수 생성함. 특히 "팀 회의록" 카테고리에만 비슷한 "주간미팅_XXX" 문서가 여러 개 있어서, 질문에 팀명/날짜가 없으면 검색 엔진이 어느 문서를 가리키는지 원천적으로 구분 불가능.
- `generate_dataset.py`의 생성 프롬프트에 "팀명/날짜/프로젝트명 등 문서를 특정할 단서를 질문에 자연스럽게 넣어라"는 규칙 추가.
- `regenerate_failed.py` 작성: retrieval_hit=0으로 실패했던 21개 문항만 골라 같은 문서 원문으로 재생성 후 같은 id에 덮어씀.
- 재검증 결과 `retrieval_hit` 0.662→**0.938**, `answer_correctness` 0.625→**0.803**로 크게 개선.

### 5-5. 남은 실패 패턴 추가 진단: "문서는 맞는데 청크가 틀림"
- 재검증 후에도 hit=1.0·faithfulness=1.0인데 correctness=0인 케이스가 다수 반복(`qa-008` 등) → 직접 재현해서 원인 확인.
- 원인: `retrieval_hit` 지표가 **doc_id 단위**로만 "찾았는지"를 판정하는데, 실제 컨텍스트로 쓰이는 건 그 문서의 특정 청크 1개뿐이었음. `qa-008`(사내 MCP 서버 모음, confluence-mcp로 뭘 할 수 있는지)의 경우 top-3가 전부 같은 문서의 "설치 과정" 청크였고, 정작 "기능 목록"이 담긴 chunk_0은 안 뽑혔음. 문서 단위로는 "hit"인데 필요한 내용은 컨텍스트에 없었던 것.
- 원인 배경: 같은 문서의 모든 청크가 동일한 제목을 갖고, 임베딩도 `f"{title}\n{text}"`로 만들어지다 보니, 제목 매치가 강한 질문에서는 같은 문서의 여러 청크가 서로 구분 없이 상위권을 독점함.
- 수정 (`es_client.py` `search_hybrid()`):
  1. BM25:kNN 가중치를 5:5 → **3:7**로 재조정 (제목 매치에 더 크게 좌우되는 BM25 비중을 낮춤).
  2. top_k "청크"가 아니라 top_k **"서로 다른 문서"**를 뽑도록 변경 (같은 문서 청크가 상위 슬롯을 독점하지 않게).
  3. 뽑힌 각 문서마다 `_fetch_full_doc_text()`로 **그 문서의 모든 청크를 chunk_index 순으로 이어붙여서**(최대 4000자) 컨텍스트로 사용 — 대표 청크 하나가 아니라 문서 전체 맥락을 넘김.
- 재검증: `retrieval_hit` 0.908, `answer_correctness` **0.837**, 실패 항목 15개→10개. (kNN 비중을 올리면서 `qa-023/029/030` 3건이 새로 실패로 전환되는 트레이드오프 발생 — 하이브리드 검색 튜닝 특성상 모든 케이스를 동시에 만족시키긴 어려움.)

### 5-6. 아직 안 고친 것 (다음에 더 엄밀하게 재검토 예정)
- **LLM judge가 피채점 모델과 동일함**: `run_qa.py`의 `faithfulness_evaluator`/`correctness_evaluator`가 모델을 지정하지 않고 `generate_chat_completion()`을 호출해서, 기본값인 `deepseek-chat`으로 채점됨 — 이는 실제 RAG 답변을 생성한 모델과 동일. Judge는 피채점 모델보다 강하거나 최소한 다른 모델을 쓰는 게 자기평가 편향(self-preference bias) 방지의 정석인데, 지금은 그렇지 않음.
- 남은 실패 10개 중 일부는 골든 라벨 자체가 애매함(`qa-025`는 정보 없는 템플릿 문서, `qa-067`은 기대답변이 질문을 그대로 되풀이하는 수준으로 부실).
- **이번에 만든 67개 데이터셋과 이 평가 결과는 "1차 러프 버전"으로 취급.** 사용자가 다음에 더 엄밀한 방식으로(어쩌면 Codex도 로컬 스크립트도 아닌 Claude 자체로) 다시 검증할 계획.
