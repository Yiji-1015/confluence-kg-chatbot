## Docker 인프라 상태

현재 `docker-compose.yml`에 정의된 서비스:

- Elasticsearch: BM25, vector kNN, hybrid retrieval 저장소
- Kibana: Elasticsearch 개발 및 검색 디버깅 UI
- TEI: `BAAI/bge-m3` 임베딩 모델 서빙
- LiteLLM: 생성 모델과 임베딩 API 게이트웨이
- Redis: 캐시 및 대화 세션 저장 후보
- Neo4j: Knowledge Graph 저장소

확인 결과:

- Docker Compose 설정 렌더링은 정상이다.
- LiteLLM 설정 볼륨은 `/app/config`에 연결된다.
- 현재 Docker 엔진은 실행되지 않아 컨테이너 상태 확인 및 기동은 하지 못했다.
- 초기 검증 우선순위는 Elasticsearch, TEI, LiteLLM이다.
- Kibana는 챗봇 실행 필수 요소가 아니라 Elasticsearch 디버깅이 필요할 때 함께 실행한다.
- Redis와 Neo4j는 Retrieval Core 검증 뒤 진행해도 된다.

## 임베딩 모델 검토

현재 계획에 기록된 선택:

- 모델: `BAAI/bge-m3`
- 서빙: Hugging Face Text Embeddings Inference(TEI)
- 벡터 차원: `1024`
- 저장소: Elasticsearch
- 서로 다른 임베딩 모델 간 자동 fallback은 사용하지 않음

선택 이유:

- 한국어와 영어가 섞인 Confluence 문서를 처리할 수 있다.
- dense retrieval에 사용할 수 있다.
- 로컬 Docker 환경에서 재현 가능하다.
- TEI가 OpenAI 호환 embedding endpoint를 제공해 LiteLLM 뒤에 연결하기 쉽다.

아직 검증하지 않은 항목:

- 실제 Confluence 문서 기준 검색 품질
- CPU 환경에서 BGE-M3 처리 속도와 메모리 사용량
- GPU 사용 필요 여부
- TEI 이미지 버전 고정
- LiteLLM에서 TEI embedding endpoint 호출
- Elasticsearch index mapping의 `dims: 1024` 일치 여부
- BM25와 vector kNN 점수 결합 방식

현재 판단:

- 모델 교체부터 하지 않는다.
- BGE-M3로 실제 문서 소량을 먼저 색인한다.
- 검색 실패 사례가 확인될 때만 다른 임베딩 모델과 비교한다.
