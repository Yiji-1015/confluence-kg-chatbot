## 1. 오늘 진행한 핵심 작업

### 1-1. 대화방(Session) 사용자 격리 (`userId` 추가)
- **문제점**: `ChatSession`에 소유자 개념이 없어 `GET /api/sessions`가 DB의 모든 세션을 반환함. 사내 공유 시 여러 사용자가 서로의 대화방을 보고 삭제할 수 있었음.
- **수정 내용**:
  - `ChatSession.java`: `@Column(name = "user_id", length = 64)` 필드 추가 및 Builder 반영
  - `ChatSessionRepository.java`: `findAllByUserIdOrderByUpdatedAtDesc(userId)` 쿼리 메서드 추가
  - `ChatRequestDto.java`, `ChatSessionDto.java`, `ChatMapper.java`: `userId` 필드 매핑
  - `ChatController.java`: `GET /api/sessions?userId=...` 파라미터 지원
  - `ChatService.java`: 세션 생성 시 `userId` 저장 및 목록 조회 시 필터링
  - `static/index.html`: `localStorage`에 `confluence_chat_user_id`가 없으면 `crypto.randomUUID()`로 생성 후 저장하고 API 호출 시 전달

### 1-2. 세션 CRUD 안전성 강화 (삭제 500 에러 방지)
- **수정 내용**: `ChatService.deleteSession(sessionId)`에서 `chatSessionRepository.existsById(sessionId)`를 먼저 검사하여, 미존재/이미 삭제된 세션 ID 요청이 와도 500 에러 없이 안전하게 멱등 처리되도록 개선.

### 1-3. 멀티턴 히스토리 Cache-Aside 복구 (Redis 30분 만료 대응)
- **문제점**: 30분 TTL 만료 후 과거 대화방을 다시 열어 질문하면 Redis 메모리가 비어있어 AI가 이전 대화 맥락을 잊어버리는 현상.
- **수정 내용**:
  - `RedisSessionService.java`: `saveHistory(sessionId, history)` 메서드 추가
  - `ChatService.java`: `getRecentHistory(sessionId)`가 비어있을 때 `recoverHistoryFromDb(sessionId)`를 호출하여 PostgreSQL `ChatMessage` 테이블의 최근 5턴(10개 메시지)을 읽어와 Redis에 다시 적재(워밍업)하는 Cache-Aside 패턴 적용.

### 1-4. RAG 시스템 프롬프트 지침 개선
- **문제점**: 시스템 프롬프트가 *"오직 문서(Context)에만 근거하라"*고만 되어 있어, "방금 내가 뭐라고 했지?" 같은 대화 맥락 질문에 "문서에 없어 모른다"고 잘못 거부하던 현상.
- **수정 내용**: `prompts.py`의 `RAG_SYSTEM_PROMPT`에 "업무 지식은 문서 [Context]에 근거하고, 이전 대화 내용 및 인사/일상 대화는 전달된 대화 히스토리(history)를 바탕으로 자연스럽고 친절하게 응답하라"는 지침 명시.

### 1-5. AI 서버 비동기(Async Non-blocking) 파이프라인 전환
- **문제점**: `chat.py`의 `process_chat`이 `async def`로 선언되어 있으나 내부에서 동기 `httpx.Client`와 동기 Elasticsearch 클라이언트를 호출하여, LLM 응답 대기(3~5초) 동안 FastAPI 메인 이벤트 루프가 블로킹되어 동시 요청이 순차 처리되던 병목.
- **수정 내용**:
  - `litellm_client.py`: `httpx.AsyncClient` 기반의 `embed_texts_async`, `generate_answer_async` 구현
  - `es_client.py`: `asyncio.to_thread` 기반의 `search_hybrid_async` 구현
  - `chat.py`: 메인 엔드포인트 내부를 `await` 비동기 호출로 전환하여, LLM 응답 대기 시간 동안 다른 사용자의 요청을 논블로킹으로 동시 처리할 수 있도록 최적화.

## 2. 주요 Q&A 및 설계 결정

### Q1. "UUID는 브라우저를 껐다 켜도 유지되나?"
- `localStorage`에 저장하므로 브라우저 종료나 PC 재부팅 후에도 동일한 UUID가 유지되어 사용자별 대화방 목록이 정상 격리됨.

### Q2. "Redis 멀티턴 세션 유지 vs 질문-답변 응답 캐시(Response Cache)"
- Redis 세션 캐시는 RDB I/O 부하를 방지하고 실시간성을 보장하는 L1 메모리 계층으로 유지.
- 질문 캐시(Response Cache)는 멀티턴 맥락 간섭, Confluence 문서 갱신 시 Stale Cache 위험 등을 방지하기 위해 1턴(독립 질문)에 한해 안전장치를 두고 추후 도입하기로 결정.

### Q3. "FastAPI의 `def` vs `async def` 동작 차이"
- `def`: FastAPI가 AnyIO 워커 스레드풀(기본 40개)로 자동 분기하여 실행.
- `async def`: 단일 메인 이벤트 루프에서 실행되므로, 내부에 동기 블로킹 코드가 있으면 서버 전체가 멈춤. 따라서 `httpx.AsyncClient`와 `await`를 사용하는 진정한 비동기 I/O로 파이프라인을 구축함.
