## 1. 오늘 진행한 핵심 작업

### 1-1. Python AI Engine (`ai-server`) 기본 인프라 구축
- `ai-server/requirements.txt`: FastAPI, elasticsearch, neo4j, redis, httpx, langchain-text-splitters, bs4 등 정의.
- `ai-server/app/config.py`: `.env` 연동 중앙 설정 클래스 (LiteLLM, ES, Neo4j, Redis, Confluence URL).
- `ai-server/app/schemas/chat.py`: API Contract 기반 Pydantic 데이터 모델 (`ChatRequest`, `ChatResponse`, `SourceDocument`, `GraphContext`).
- `ai-server/app/api/v1/chat.py`: 메인 채팅 엔드포인트 (`POST /internal/chat`).
- `ai-server/app/main.py`: FastAPI 실행 진입점 및 헬스체크 (`GET /internal/health`).

### 1-2. Confluence 표/링크 보존 파서 & 청커 (`app/parser/confluence_parser.py`)
- BeautifulSoup 기반 HTML 파싱: `<table>` 태그를 마크다운 표(`| 제목 | 내용 |`)로 보존하여 RAG 검색 시 구조 파괴 방지.
- `RecursiveCharacterTextSplitter` (chunk_size: 800자, chunk_overlap: 150자).
- 고유 `chunk_id` (`doc_id_chunk_idx`) 자동 생성 로직 반영.

### 1-3. Confluence 수집 & 증분/삭제 추적 모듈 (`app/core/confluence_client.py`)
- `fetch_all_page_ids()`: Confluence 삭제 감지용 전체 ID 목록 가볍게 수집 (Diffing 동기화용).
- `fetch_confluence_pages()`: 전체 수집 및 `modified_since` 파라미터를 통한 증분 수집 지원.
- `fetch_page_by_id()`: 단건 상세 조회.

### 1-5. Elasticsearch 하이브리드 검색 모듈 (`app/retrieval/es_client.py`)
- `create_confluence_index()`: Nori 한국어 형태소 분석기 + 1024차원 Dense Vector(BGE-M3) 인덱스 매핑 자동 생성.
- `index_document_chunks()`: `chunk_id`를 Elasticsearch의 Primary Key(`_id`)로 등록하여 Bulk 색인 및 자동 덮어쓰기(Upsert) 보장.
- `search_hybrid()`: BM25 키워드 매칭(제목 가중치 2.0배 `title^2.0`) + BGE-M3 코사인 유사도 Vector kNN 검색 결합.
- `delete_documents_by_ids()`: Confluence 삭제 문서 ID 목록을 전달받아 Elasticsearch에서도 `delete_by_query`로 일괄 삭제 동기화.
- 메인 채팅 라우터 (`app/api/v1/chat.py`)에 하이브리드 검색 연동 및 Elasticsearch 미기동 시 안전한 Fallback 로직 추가.

### 1-6. 코드 주석 보강
- `confluence_parser.py`, `confluence_client.py`, `es_client.py` 등 작성된 모든 파이썬 모듈에 한글 docstring과 상세 주석 추가 완료.

## 2. 주요 아키텍처 Q&A 및 개념 정리 (이론 & 설계)

### Q1. "다 ai-server에 넣나? 그럼 MVC(Spring Boot)는 무슨 일을 하는가?"
- **Spring Boot (MVC 백엔드)**: 사용자 인증/권한, 외부 REST API Gateway, 대화 세션/히스토리 DB(Redis/RDB) 저장, Job 상태 관리.
- **Python FastAPI (`ai-server`)**: AI Engine (RAG, 하이브리드 검색, 문서 파싱, GraphRAG, LiteLLM 연동).
- **이유**: 네이버/카카오 등 엔터프라이즈 AI 서비스의 표준 아키텍처 (웹 백엔드 ↔ AI 미크로서비스 분리).

### Q2. "프론트엔드(React/Lovable)까지 붙이면 너무 비대해질까?"
- 백엔드(Spring Boot)가 REST API만 반환하므로 프론트엔드는 가벼운 SPA(Single Page App)에 불과함.
- 개발 순서는 `ai-server` ➔ `Spring Boot` ➔ `React Frontend` (Phase 7) 순으로 진행.

### Q3. "REST API 주소는 컨트롤러에서 결정되나? API 정의부터 해야 하나?"
- **API-First Design (Contract-First)**: 개발 전 `POST /internal/chat` 및 `POST /api/chat` JSON 데이터 규격을 먼저 협의한 뒤 개발 진행.

### Q4. "포트폴리오니까 내가 100% 설명 가능한 익숙한 코드가 중요함. 클래스 대신 `def` 함수로 가능한가?"
- [AGENT_RULES.md](AGENT_RULES.md)에 **"직관적이고 설명 가능한 코드: 꼭 필요한 경우가 아니면 클래스 대신 함수(`def`) 기본 사용"** 규칙 명시.
- 파서 및 수집 모듈을 파이썬 순수 함수(`def`) 형태로 직관적으로 구현.

### Q5. "GraphRAG는 Phase 5에 할 건데, 그래프 없이도 일단 돌아가게 둘 수 있나?"
- `graphContext = None` (기본값)으로 설계.
- Knowledge Graph(Neo4j) 없이도 Elasticsearch 하이브리드 검색만으로 100% 완벽히 작동함.
- Phase 6에서 "GraphRAG 추가 전/후 검색 정확도 비교 평가"를 위한 플러그인 구조 유지.

### Q6. "증분 수집 및 삭제 추적이 가능한가?"
- **증분 수집**: `modified_since` 파라미터로 지정 시각 이후 변경된 문서만 선택 수집.
- **삭제 추적**: Confluence의 살아있는 전체 `page_id` 목록과 Elasticsearch 저장 목록을 비교(Diffing)하여 삭제된 문서를 감지하고 ES에서 `delete_by_query` 처리.

### Q7. "파싱에 Upstage API를 안 써도 되나?"
- Confluence API가 이미 HTML 구조(`<table>`, `<a>`)로 응답을 주므로 유료 API 없이 `BeautifulSoup`만으로 비용 0원 & 초고속 파싱 가능.
- Upstage API는 향후 PDF/이미지 첨부파일 파싱 확장 시 검토.

### Q8. "실험용 노트북(.ipynb)과 Langfuse의 차이는?"
- **노트북 (.ipynb)**: 파싱/청킹 결과(표 보존, 청크 오버랩)를 눈으로 직관적으로 검증하는 **개발 실험 도구**.
- **Langfuse**: 최종 챗봇 작동 시 검색된 `chunk_id`, 소요 시간, 토큰, LLM 비용, 정답률을 관측하는 **운영/평가 모니터링 도구**.

### Q9. "청크 ID (`chunk_id`) 생성 및 연동 구조"
- `doc_id` + `chunk_idx` (예: `doc-101_chunk_0`).
- Elasticsearch 문서의 Primary Key(`_id`)로 사용하여 덮어쓰기(Upsert) 및 삭제 지원.
- Langfuse Trace에 검색된 핵심 식별자로 기록.

### Q10. "하이브리드 검색 결합 점수(Scoring) 방식과 도메인 선택 이유"
- **선택 방식**: 제목 가중치 2.0배 (`title^2.0`) 부여 BM25 + BGE-M3 코사인 유사도 Vector kNN의 순수 점수 결합 (Direct Combined Scoring).
- **선택 이유**: 사내 Confluence 도메인 특성상 사용자들이 명확한 키워드나 문서 제목으로 검색하는 경향이 압도적임. 따라서 제목 키워드 매칭을 최우선으로 가산하고, 키워드가 어긋나는 경우 Vector 유사도가 하이브리드로 보완하도록 설계.

### Q11. "Langfuse에서 BM25 vs Dense Vector 채택 비율 관측 가능 여부"
- 가능함. 하이브리드 검색 후 Span Metadata에 `bm25_hit_count`, `dense_hit_count`, `overlap_count`를 기록하여 대시보드 및 평가 보고서 데이터로 시각화 예정.

## 4. ELASTICSEARCH.md 기준과 구현 불일치 수정 및 인프라 검증

작업을 이어가기 전 `docs/ELASTICSEARCH.md`(최신 승인 기준)와 실제 구현이 어긋나 있는 것을 발견해 먼저 정리했다.

### 4-1. 발견한 불일치

- `es_client.py`가 주석으로는 "ELASTICSEARCH.md 준수"라 해놓고 실제로는 구버전 설계(BGE-M3, 1024차원)를 그대로 사용.
- `config.py`의 `DEFAULT_EMBEDDING_MODEL`, `ELASTICSEARCH_INDEX`도 BGE-M3/로컬 기준값.
- `docker-compose.yml`의 elasticsearch 서비스가 `xpack.security.enabled=false`, TLS 없음, 포트 전체 공개, healthcheck 없음 — ELASTICSEARCH.md가 요구하는 보안 기준과 불일치.
- `litellm/config.yaml`은 이미 OpenAI `text-embedding-3-small`로 맞춰져 있어 ELASTICSEARCH.md와 일치. 이 기준으로 나머지를 정렬하기로 결정.

### 4-2. 수정 내용

- `ai-server/app/retrieval/es_client.py`: dense_vector `dims`를 1024 → 1536으로 수정, 관련 주석을 OpenAI text-embedding-3-small 기준으로 정리. `get_es_client()`에 TLS(`ca_certs`)와 basic auth 추가.
- `ai-server/app/config.py`: `DEFAULT_EMBEDDING_MODEL=embedding-openai`, `ELASTICSEARCH_INDEX=confluence-openai-v1`, `ELASTICSEARCH_URL=https://localhost:9200`로 변경. `ELASTICSEARCH_USER`, `ELASTICSEARCH_PASSWORD`, `ELASTICSEARCH_CA_CERT` 필드 추가. `.env`와 CA 인증서 경로를 실행 위치(cwd)와 무관하게 저장소 루트 기준 절대경로로 계산하도록 수정 (`REPO_ROOT = Path(__file__).resolve().parent.parent.parent`) — 기존에는 `ai-server/`에서 uvicorn을 실행하면 repo 루트의 `.env`를 못 찾는 잠재 버그가 있었다.
- `ai-server/requirements.txt`: `elasticsearch` 클라이언트를 `<9.0.0`으로 고정. 최신 9.x 클라이언트는 ES 8.15 서버와 HTTP Accept 버전이 안 맞아 모든 요청이 400 에러(`media_type_header_exception`)를 냄.
- `docker-compose.yml`:
  - `es-setup` 서비스 추가: `elasticsearch-certutil`로 CA/노드 인증서를 최초 1회 생성해 `./elasticsearch/certs`(호스트 bind mount, gitignore 처리)에 저장.
  - `elasticsearch` 서비스: `xpack.security.enabled=true` + HTTP/Transport TLS 활성화, `127.0.0.1:9200`으로만 바인딩, `mem_limit`을 `ES_MEMORY_LIMIT` env로 분리(기존 `-Xms1g -Xmx1g` 고정값 제거), `_cluster/health` 기반 healthcheck 추가.
  - `kibana-setup` 서비스 추가: `elastic` superuser는 Kibana가 시스템 인덱스에 쓸 수 없어 거부되므로(`value of "elastic" is forbidden`), `kibana_system` 계정 비밀번호를 부트스트랩 시점에 API로 설정.
  - `kibana` 서비스: `kibana_system` 계정으로 접속하도록 변경, `127.0.0.1:5601`로만 바인딩.
- `.env` / `.env.example`: `ELASTIC_PASSWORD`(compose용), `ELASTICSEARCH_PASSWORD`(ai-server용, 같은 값), `KIBANA_PASSWORD`, `ES_MEMORY_LIMIT` 추가.
- `.gitignore`: `elasticsearch/certs/` 추가.

### 4-3. 시행착오 / 주의사항

작업 중 실제로 겪은 오류와 원인, 재발 방지 포인트. 앞으로 이 Compose 스택을 다시 만지거나 비슷한 ES+TLS 구성을 할 때 참고.

1. **`elasticsearch-certutil cert`의 기본 인증서 폴더명은 `instance/`다.**
   `--name` 옵션을 안 주면 `elasticsearch/elasticsearch.crt`가 아니라 `instance/instance.crt`로 생성된다.
   compose의 `xpack.security.http.ssl.certificate=certs/elasticsearch/elasticsearch.crt` 경로와 어긋나 ES가 인증서를 못 찾는다.
   → `elasticsearch-certutil cert ... --name elasticsearch`로 이름을 명시해야 한다.

2. **Docker healthcheck `test` 문자열 안의 `&`는 셸 메타문자다.**
   `https://localhost:9200/_cluster/health?wait_for_status=yellow&timeout=5s`처럼 URL을 따옴표 없이 그대로 넣으면,
   `&`에서 명령이 백그라운드로 갈리고 뒤의 `timeout=5s`가 별도 명령으로 취급되어 `grep`이 빈 입력을 받아 항상 실패(exit 1)한다.
   API 자체는 정상 응답(`"status":"green"`)했는데 healthcheck만 계속 `starting`으로 남아 있어서 원인 파악에 시간이 걸렸다.
   → URL 전체를 큰따옴표로 감싼다(`"https://...&..."`). curl/wget 등을 healthcheck에 넣을 때는 항상 URL을 따옴표로 감쌀 것.

3. **`elasticsearch` 파이썬 클라이언트를 버전 상한 없이 설치하면 서버와 프로토콜이 깨진다.**
   `requirements.txt`에 `elasticsearch>=8.15.0`(상한 없음)로 적혀 있어 pip가 최신 9.x를 설치했다.
   9.x 클라이언트는 `Accept: application/vnd.elasticsearch+json; compatible-with=9` 헤더를 보내는데,
   서버는 ES 8.15라 7/8만 허용 → 인덱스 생성, 색인, 검색, 삭제 등 **모든 요청이 400 `media_type_header_exception`으로 실패**했다.
   에러 메시지가 인증/매핑 문제처럼 보여서 헷갈리기 쉽다. 서버 버전과 클라이언트 major 버전은 항상 맞춰야 한다.
   → `elasticsearch>=8.15.0,<9.0.0`으로 상한을 고정.

4. **Kibana는 `elastic` superuser 계정으로 접속할 수 없다.**
   `elastic`로 `ELASTICSEARCH_USERNAME`을 주면 Kibana가 부팅 단계에서
   `"value of \"elastic\" is forbidden. This is a superuser account that cannot write to system indices"`로 즉시 죽는다.
   → 반드시 `kibana_system` 내장 서비스 계정을 쓰고, `_security/user/kibana_system/_password` API로 비밀번호를 먼저 설정해야 한다(이번에 `kibana-setup` 서비스로 자동화).

5. **pydantic-settings의 `env_file=".env"`는 실행 위치(cwd) 기준 상대경로다.**
   `ai-server/app/config.py`가 `.env`를 상대경로로 참조하고 있었는데, 실제 `.env`는 저장소 루트에 있다.
   PLAN.md가 안내하는 실행 방식대로 `ai-server/` 디렉터리에서 `uvicorn app.main:app`을 실행하면 cwd가 `ai-server/`가 되어
   **`.env`를 못 찾고도 에러 없이 조용히 기본값으로 fallback**한다 (Confluence 토큰, ES 비밀번호 등이 전부 비어있는 채로 실행될 뻔했다).
   → `Path(__file__).resolve().parent.parent.parent`로 저장소 루트를 계산해 절대경로로 고정. `ELASTICSEARCH_CA_CERT` 기본값도 동일하게 처리.
   앞으로 cwd에 의존하는 상대경로 설정을 추가할 때는 항상 이 패턴을 의심할 것.

### 5-5. `pre/`(예전 프로젝트) 참고해 파서/카테고리 로직 보강

`pre/`가 이 저장소에서는 빈 폴더(깨진 git submodule 참조)로 남아있어서, 원본 저장소(`https://github.com/Yiji-1015/Confluence_Chatbot`, PLAN.md에 명시된 원본)를 스크래치패드에 클론해서 예전 구현을 직접 참고했다. 발견한 개선점을 반영:

- **`confluence_parser.py` 전면 개선**:
  - 표 파싱을 `rowspan`/`colspan`을 그리드로 펼쳐서 처리하도록 변경 (`_table_to_records`, `_table_records_to_markdown`). 기존 방식은 병합 셀이 있는 표에서 컬럼이 밀리는 문제가 있었음.
  - Confluence 내부 문서 링크(`ac:link` + `ri:page`)를 `[본문](관련문서: 제목)` 형태로 보존하도록 추가. 기존 파서는 `<a href>`만 처리해서 실제 Confluence storage 포맷의 내부 링크(`ac:link`)를 전부 놓치고 있었음.
  - 첨부파일(`ri:attachment`) 파일명 추출 추가 (기존엔 전혀 처리 안 했음).
  - 매크로 노이즈 태그(`ac:parameter`, `ac:schema-version`, `ac:macro-id`, `ri:url` 등) 제거 및 나머지 네임스페이스 태그(`ac:*`, `ri:*`) unwrap 추가 — 매크로가 본문에 이상한 텍스트로 섞여 나오는 것 방지.
  - 실제 문서(표 있는 문서, `ac:link` 있는 문서, 첨부파일 있는 문서)로 개별 검증 완료.

- **`confluence_client.py`에 카테고리 조회 기능 추가** (`pandas` 신규 의존성 추가, 사용자 승인):
  - `fetch_pages_with_category()`: `expand=ancestors`로 문서마다 조상 페이지 제목 목록을 받아와 `path`(예: "기획 / 팀 회의록 / ...")와 `level_0, level_1, ...` 컬럼으로 정리한 DataFrame 반환.
  - `filter_pages_by_category(df, {"level_1": "솔루션/개발"})`: 카테고리 레벨 기준으로 문서 ID만 필터링.
  - `fetch_pages_by_ids()`: 필터링된 ID 목록만 골라서 본문 조회.
  - **버그 발견 및 수정**: 처음 구현에서 path를 문자열로 합쳤다가 `/`로 다시 쪼개는 방식을 썼는데, "솔루션/개발"처럼 **카테고리 제목 자체에 `/`가 포함된 경우** 계층이 잘못 쪼개지는 문제가 실제로 발생했다 (level_1이 "솔루션"으로 끊기고 "개발"이 별도 레벨로 분리됨). 조상 제목 리스트를 문자열 왕복 없이 그대로 보존하도록 수정해서 해결.
  - 실제 스페이스 카테고리 구조 확인: 기획(133), 팀 회의록(133), 환영합니다(114), Project(87), 솔루션/개발(41), 피앤씨(20), 마케팅(15), 세일즈(2) 등.

- **재색인 시 고아 청크(orphaned chunk) 방지**: `ingest.py`에서 색인 전에 대상 문서들의 기존 청크를 `delete_documents_by_ids()`로 먼저 삭제하도록 추가. (예전 프로젝트의 `delete_page_vectors()` 패턴 참고 — 문서가 짧아져서 청크 수가 줄면, 이전 버전의 뒷쪽 청크가 삭제 없이 그대로 남아있을 수 있는 문제를 예방)
- **임베딩용 텍스트에 제목 포함**: BM25는 이미 `title^2.0` 가중치를 따로 주고 있어 저장용 `text` 필드는 그대로 두되, 벡터 임베딩 생성 시에는 `"{title}\n{text}"`를 넣어 청크가 문서 제목 맥락을 벡터 공간에서도 유지하도록 함 (예전 프로젝트의 청크 제목 병합 패턴 참고).
- **의도적으로 보류한 것** (범위 밖, 나중에 필요 시): `get_primary_contributor()`(버전 히스토리 기반 최다 수정자 탐색 — PLAN.md의 KG `TOP_CONTRIBUTOR` 관계, Phase 5 대상), `updated_at` 비교 기반 증분 재색인 skip 로직(PLAN.md Phase 1 "incremental indexing"과 관련 있지만 이번 배치에는 포함 안 함), children 매크로 자동 하위 목록 삽입 기능.

### 5-6. `scripts/ingest.py` 신규 작성 — Phase 1 파이프라인 통합 스크립트

수집 → 파싱 → 청킹 → (재색인 대상 기존 청크 삭제) → 임베딩 → Elasticsearch 색인까지 한 번에 실행. `--limit`(문서 수 제한), `--category`(대분류 필터), `--batch-size`(임베딩 배치 크기) 옵션 지원.

**검증 결과**:
- `--limit 5`로 5개 문서 → 10개 청크 소규모 테스트 성공, 실제 검색("개발")도 정상 작동 확인.
- `--category "솔루션/개발"`로 41개 문서 → 73개 청크 실제 색인 성공, 검색 결과도 정상.
